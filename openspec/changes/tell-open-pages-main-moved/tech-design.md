Drawn from [Change Stages · Surfaces](../../../docs/prds/products/shared/planning/change-stages.md#surfaces), the proposal and the journeys, before the requirements. The requirements pass reads it; the reconciliation re-reads it.

## Context

- **The hosted manual is a static snapshot.** `tools/manual/src/store/build-snapshot.mts` writes `dist/api/snapshot`, `dist/api/archive` and one file per change and reference; `SnapshotFooter` names `snapshot.storeHead`, the commit the build read. `manual.yml` rebuilds and redeploys on every push to `main` that touches the paths it watches.
- **The dev server serves the same shapes from disk.** `storeEndpoints` in `tools/manual/src/store/vite-plugin.mts` answers `/api/snapshot`, `/api/change/<id>`, `/api/propose`, `/api/hands` and the rest behind one path allowlist, so a new endpoint is one branch there and one file in the build.
- **The relay is one Worker with one Durable Object.** `tools/relay/src/worker.ts` routes `/slack/events`, `/wake` and `/runs/<token>/<op>`, refuses every request while one of the seven secrets is unset (`missingSecret`), and answers 405 to anything but POST except `/runs/<token>/alive`. `Room` is the only Durable Object class, created by migration `v1`.
- **The signature work already exists.** `hmacSha256`, `fromHex` and `equalBytes` in `src/bytes.ts` verify Slack's v0 signature in `src/slack.ts`; the code host's `x-hub-signature-256` is the same HMAC over the raw body with a different prefix.
- **Nothing in the store watches `main`.** No workflow, no endpoint and no page compares a checkout or a snapshot with `origin/main`.

## Goals / Non-Goals

**Goals:**

- One head, held by the relay, read the same way by every open page
- A page that says it is behind at once and refreshes itself only when the site can show what landed
- A locally run manual that reads its own distance from `main` and fast-forwards on one click
- Every leg off by default: no relay URL, no banner, and the manual reads as it does today

**Non-Goals:**

- A socket per change, per page or per reader beyond the one the shell opens
- Serving the store's data live: the snapshot is still built by the deploy
- Any write to the store from the hosted site
- A merge, a rebase or a stash on the teammate's behalf

## Decisions

The page governs what a reader is told; these are how that lands.

- **The head comes from the code host's push webhook.** `POST /github/events` on the relay: the raw body is read once, `x-hub-signature-256` is verified as `sha256=<hex>` against `GITHUB_WEBHOOK_SECRET` with `hmacSha256` and `equalBytes`, and an unsigned or wrongly signed body answers 401 without reaching a Durable Object. The handler reads `ref`, `after`, `repository.full_name` and the first line of `head_commit.message`, and stamps the head with the object's own clock at the move, so the age a page shows is since the push arrived, never the commit's own time; anything but `refs/heads/main` of `REPO` answers 200 and is dropped, so a branch push, a tag and another repository cost one HMAC and nothing else. Rejected: the browser polling the code host, which needs a token in the page and rate-limits per reader; a poll of the deployed snapshot alone, which cannot name what landed until the deploy is done (decisions Q1).
- **`GITHUB_WEBHOOK_SECRET` is the eighth required secret.** Added to `Env` and to `REQUIRED_SECRETS`, so a relay deployed without it answers `{"reason":"missing-secret","secret":"GITHUB_WEBHOOK_SECRET"}` with 500 and names itself, as the other seven do. Rejected: verifying the webhook only when the secret is set, which turns a missing secret into an open endpoint.
- **One `Live` Durable Object holds the head.** Binding `LIVE`, class `Live`, migration `v2` with `new_sqlite_classes: ["Live"]`, addressed as `idFromName("main")` - one object for the store, because there is one `main`. It stores `{ main, at, subject }`: the head sha, the stamp the object takes from its own clock as the delivery arrives, and the commit's subject line. `at` is the arrival rather than the commit's own timestamp, so the age a page shows is how long ago the push arrived - a commit can be hours older than the push that carried it, and what the reader is waiting on is the push. A push writes that record and broadcasts it to every socket; writing the same sha twice broadcasts once, because the set is compared before it is stored. Rejected: a room per change, which would make a reader on the board open one socket per card.
- **Sockets hibernate.** `GET /live` upgrades through `ctx.acceptWebSocket(server)` and sends the stored record on accept, so a page that connects after the push still learns the head; a move calls `getWebSockets()` and sends the same JSON to each. Hibernation is what makes an idle open tab free - the object is evicted between pushes and the socket survives it - and it is why no per-socket state is kept beyond what the accept tags carry. The object answers each `ping` with `pong` from the runtime's auto-response pair without waking; the page sends one every 30 s and closes a line into the ladder when two pings bring nothing back.
- **`GET /head` is the fallback and the smoke test.** It answers the same JSON with `access-control-allow-origin: *`, because the hosted manual is served from another origin and the record says nothing private: a commit sha and a subject line already on `main`. The router's method gate gains the two GET routes beside `/runs/<token>/alive`. Rejected: a signed read, which would put a credential in a static page.
- **The relay's origin reaches the browser as data, never as a build constant.** `GET /api/relay` answers `{ url?: string }`: the dev server reads `process.env.RELAY_URL`, and the build writes `dist/api/relay` from `RELAY_URL` in the environment. An absent or empty value answers `{}`, the watch opens nothing, and no banner is ever shown - which is the off switch Operations holds without a revert (decisions Q3). Rejected: baking the origin into the bundle, which puts a deploy-time value into a file the hosted site serves; and the name `/api/live`, which the app already spends on its own HMR event module and which a static site answers with `index.html` wherever it serves no such file, so a smoke read of the wrong name passes.
- **One line, a ladder, then a poll.** `watchMainHead` in `src/api/head.ts` reads `/api/relay` once and opens `wss://<relay>/live` where the browser has a socket. A line that drops is opened again after 1 s, 2 s, 5 s, 15 s and 30 s, and a head arriving resets the ladder; once the ladder is exhausted, and wherever the browser has no socket at all, the watch polls `GET /head` every 60 s instead. `useMainHead` wraps it and returns the record it holds and nothing else: the comparison is the banner's.
- **Behind is `main` against the head the page booted from.** The banner shows as soon as the relay's head differs from `snapshot.storeHead`, naming the subject and the age from the record. While behind, the shell polls `GET /api/head` - `{ storeHead }`, answered by the dev plugin from the checkout and by `dist/api/head` from the build - every 30 s and compares it with the head the page booted from, not with `main`: the site has caught up the moment those two differ, whatever `main` has done since. The store is then re-read through the snapshot provider, never `location.reload()`, so the reader keeps their scroll position, their open sections and anything typed. After ten minutes behind the banner drops the promise that the site refreshes itself and the poll backs off (decisions Q9). Rejected: refreshing on the webhook, which serves the reader the same page again because the site has not rebuilt yet (decisions Q2); and holding the deployed snapshot's head in the `Live` object so a page could be told the site has caught up rather than polling for it, which needs the deploy to post back to the relay - the deploy's change, not this one, and the poll answers the same question with nothing new deployed.
- **Nothing is reloaded under a reader who is typing.** The re-read is held while the focused element is a text field, a text area or a `contenteditable` - any of them, wherever it sits (decisions Q8) - and a `focusout` listener takes a held re-read the moment focus leaves, rather than leaving the reader on the old page until the next poll; the banner stays up meanwhile, so they know why the page has not moved. Rejected: reloading anyway and restoring the draft, which needs the editor's state in the shell.
- **The hosted site rebuilds on every push to `main`.** `manual.yml` loses its `paths:` filter: the banner says the site rebuilds and refreshes on its own, and a filtered deploy makes that false on every push that touches none of the watched paths - `tools/relay/**` and `scripts/openspec/**` among them - leaving the banner up until an unrelated push happens to touch one. Beside the filter, `manual.yml` gains a `workflow_run` trigger on Lint: Lint's own `chore(ci): apply Biome lint fixes` push is made with the default token, which fires the push webhook and starts no workflow, so that one push moves `main` under every open page with nothing coming to catch it up (decisions Q7). `workflow_dispatch` and the `manual-staging` concurrency group with `cancel-in-progress` stay, so a burst of pushes still deploys once. Rejected: filtering the webhook by the paths the manual renders, which puts the manual's path list inside the relay and drifts the day either moves.
- **The locally run manual reads git, not the relay.** `GET /api/upstream` in the dev server's endpoints answers one record, `{ behind, ahead, dirty, fetchedAt? }`: `git fetch origin main` at most once every 60 s - the last fetch's time is held in the plugin's own memory - then `git rev-list --left-right --count HEAD...origin/main` for the pair of counts and `git status --porcelain` for whether the tree holds anything uncommitted. The counts are read every time against whatever refs the clone has, so the record answers with or without a fetch; `fetchedAt` absent says `origin` has never been read - a checkout with no remote, or one whose fetches have all failed - and a checkout with nothing to count against shows no banner (decisions Q6). Rejected: a fetch per request, which spends a network call on every render (decisions Q4); and a second shape for a checkout with no remote, which asks every reader of the record to handle two.
- **The local half is gated on a dev server answering, and polls the minute.** `/api/dirty` is the one endpoint no built site serves, so it is the probe: where it answers, the shell reads the checkout; on the hosted site nothing is asked at all. The standing is polled every 60 s, the same minute the dev server throttles its fetch to, so a second tab costs a status call rather than a second fetch - and it is read again at once when the relay says `main` moved, so the banner's two lines agree with each other. A refusal from a press is held until the next press, so the poll under the reader never clears the reason they are looking at.
- **Pull is `--ff-only`, and refuses rather than decides.** `POST /api/pull` runs `git pull --ff-only origin main` behind the same confinement as `/api/propose` and answers `200 { pulled: true, head }` with the commit the checkout landed on. All three refusals - a tree holding uncommitted work, a checkout holding a commit `main` does not, and a fast-forward git itself refuses - answer `409 { error }` carrying git's own words, so nothing of the teammate's work is stashed, merged or rebased and nothing invents a reason git did not give. What the reader sees before they press is read off the standing rather than off this answer: Pull is not offered at all while the checkout is dirty or ahead, and the banner's own line says which. One pull is in flight per checkout, and a second press while one is running is dropped rather than starting a second git. Both git legs run under a 30 s timeout with `GIT_TERMINAL_PROMPT=0`, so a clone whose `origin` asks for a credential fails instead of holding the dev server open.
- **`manual.yml` passes `RELAY_URL` as a repository variable.** `RELAY_URL: ${{ vars.RELAY_URL }}` on the build step alone, not a secret: the value is a public origin the page has to hold anyway, and a secret would be masked out of the file the build writes. Unset is the off state, and the deploy is unchanged otherwise.

## Service Interfaces

Not a service. The contracts that cross a boundary:

| Contract | Input | Output |
| --- | --- | --- |
| `POST /github/events` (relay) | The push event's raw body, `x-github-event` and `x-hub-signature-256` | The live object's own `{ moved, told }` once the head is taken; `{ pong: true }` for the `ping` the host sends as the webhook is saved; `{ ignored: <why> }` over the closed set `not-a-push`, `another-repository`, `another-branch`, `no-commit`; 401 on a bad or missing signature; 400 only on a body that is not JSON |
| `GET /head` (relay) | Nothing | `{ main, at, subject }`, or `{ main: null }` before the first push, with `access-control-allow-origin: *` |
| `GET /live` (relay) | A WebSocket upgrade | The stored record on accept, then the same JSON on every move; 426 to a read that is not an upgrade |
| `Live` (Durable Object) | `idFromName("main")`; one typed op, `{ op: "moved", push }` or `{ op: "head" }` | The stored record, and one broadcast per new sha. What the next head is and who is told is `live-state.ts`, pure and read in a test with no storage and no socket |
| `GET /api/relay` (manual) | Nothing | `{ url }` where the build or the dev server has one, else `{}` |
| `GET /api/head` (manual) | Nothing | `{ storeHead }`: the commit the served snapshot was built from |
| `GET /api/upstream` (manual, dev server only) | Nothing | One record, `{ behind, ahead, dirty, fetchedAt? }`: the two counts against `origin/main`, whether the tree holds anything uncommitted, and when `origin` was last read - absent where it never was |
| `POST /api/pull` (manual, dev server only) | Nothing | `200 { pulled: true, head }` once the fast-forward lands; `409 { error }` in git's own words on a dirty tree, a checkout ahead, or a fast-forward git refuses |
| `watchMainHead({ onHead, http, open, wait })` (manual) | The relay read through `http`, the line through `open`, the clock through `wait` | Each head `main` reaches, in order, through `onHead`; the ladder and the 60 s poll are driven by a test rather than waited for. `open: null` is a browser with no socket |
| `watchDeployedHead({ head, reload, http, typing, wait })` (manual) | The head the page booted from, the store's own re-read, and the three seams | The re-read, called once the site's head differs from the booted one and no reader is typing; the stop cancels the poll |
| `watchCheckout` (manual, where a dev server answers) | The standing read through `http`, the clock through `wait` | The standing every minute and on demand, which `useCheckout` wraps with the pull and the refusal it holds until the next press |
| `originMain(root, now)` (manual, the dev server's own) | The checkout's root and the clock | `standing()` and `pull()` over that one checkout, the fetch throttle held per dev server so two tabs share one fetch |
| `useMainHead()` (manual) | Nothing | The relay's record, or nothing at all where there is no relay |

The record, as the socket and `GET /head` both send it:

```json
{
  "main": "8f2c1d0e5a7b9c3d4e6f8a1b2c3d4e5f60718293",
  "at": "2026-09-20T04:11:07Z",
  "subject": "docs(planning): land the requirements of tell-open-pages-main-moved"
}
```

## Risks / Trade-offs

- [A delivery is replayed, or the host sends the same push twice] → the same sha writes nothing and tells nobody, because the set is compared before it is stored; a replay of an older delivery carries a different sha and does set the head back to that commit, which every open page then reads as `main`. Redeliver is a hand's act in the host's own delivery log rather than something the relay does to itself, and it stays bounded: a page ten minutes behind drops the banner's promise and backs its poll off, and the next push to `main` corrects the head (decisions Q9)
- [A busy `main` floods every open page] → one broadcast per push, not per commit, and the payload is three fields; a reader behind by ten pushes has been told ten times and reloads once, when the deploy catches up
- [The relay is down while `main` moves] → no banner, and the manual reads as it does today; the page is stale and silent rather than wrong
- [A reader sits on the banner for an hour] → the 30 s poll of `GET /api/head` is what ends it, not the socket, so a socket that died unnoticed still lets the page catch up; from ten minutes the poll backs off and the banner says the site has not caught up rather than promising again that it will
- [Pull lands on a checkout somebody else is building in] → `--ff-only` and the dirty refusal: nothing is pulled over uncommitted work, and the reason names it
- [`RELAY_URL` is set to the wrong origin] → the page opens a socket that never answers, falls back to the poll, gets nothing, and shows no banner; nothing else on the page depends on it
- [Deploying on every push to `main` costs more runs] → the `manual-staging` concurrency group with `cancel-in-progress` collapses a burst into one deploy, and the build is the one the watched paths already ran

## Migration Plan

1. `GITHUB_WEBHOOK_SECRET` set on the relay, then the deploy that carries `POST /github/events`, the `Live` class and migration `v2`, `GET /head` and `GET /live` - the secret first, because the entry refuses every surface while one of the eight is unset, which is the order `tools/relay/README.md` gives. Deployed with no webhook registered it holds no head and answers `{ main: null }`; nothing else in the relay changes.
2. Operations registers the push webhook, which can only follow the deploy that set the real `REPO`: every push before it answers `another-repository`. After the next push to `main`, two reads are the smoke test, the two a page makes - `curl -s "$RELAY_URL/head"` answers the sha `main` is on, and a socket read of `$RELAY_URL/live` over `wss:` is sent the same record on accept.
3. The locally run manual's half: `/api/upstream`, `/api/pull` and the banner's local variant. It needs neither the relay nor the variable, so it lands ahead of the wait rather than behind it. Both halves are one change because they are one banner slot and one hook file: the reader has one question, and two changes would put two notices in the same place.
4. The manual's hosted half: `/api/relay`, `/api/head`, the head watch and the banner, with `RELAY_URL` still unset. Nothing appears until Operations sets the variable, so this step ships dark.
5. `RELAY_URL` on the repository variables, `manual.yml` passing it to the build step, its `paths:` filter dropped and its `workflow_run` trigger on Lint added (decisions Q7). `curl -sf <site>/api/relay` answers the origin and `curl -sf <site>/api/head` the snapshot's own head; a 404 from either is a build that wrote neither file. Rollback for the whole hosted half is deleting that variable and re-running the workflow.
