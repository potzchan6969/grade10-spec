## Context

Google sign-in already reaches the browser as a rendered button: `packages/grade10-auth/frontend/src/features/session/sign-in/domain/usecases/MountGoogleSignInButton.ts` calls `BetterAuthSignInRepository`'s `oneTap({ button: { container, config } })`, which better-auth's client (`node_modules/better-auth/dist/plugins/one-tap/client.mjs`) turns into `google.accounts.id.renderButton(...)`. Omitting `button` drives the other branch instead — `google.accounts.id.prompt(...)`, Google's own auto-popping corner UI — with built-in retry/backoff on a dismissed or skipped moment. Nothing in the repository calls it that way today.

The button mounts inside `SignInCard`, itself inside `SignInOverlayProvider` (`packages/grade10-auth/frontend/src/features/session/sign-in/presentation/overlay/signInOverlay.tsx`), which both `apps/frontend/grade10/src/root.tsx` and `apps/frontend/zzz/src/root.tsx` wrap around their whole tree and expose through `useSignInOverlay()` (`{ open, openSignIn, closeSignIn, signedIn }`). Both apps already gate on `useSession()` and the same brand check (`packages/app-env`'s Google-offered lookup) that the button uses.

## Goals / Non-Goals

**Goals:**
- Drive `google.accounts.id.prompt()` for a signed-out visitor, gated the same way the button already is, on both apps that share `SignInOverlayProvider`.
- Never let the prompt and the sign-in dialog be visible at once, in either direction.
- Suppress the prompt for the rest of the visit once a visitor has actively engaged with sign-in and walked away.

**Non-Goals:**
- zzz's Google client id, admin/operator apps, staged rollout, per-page exclusions — all out of scope per `decisions.md`.
- A design-system component: the prompt is Google's own chrome, nothing under `packages/ui` or `packages/design-system` changes.

## Decisions

**Two new use cases beside the existing one, not a modification of it.** `MountGoogleSignInButton` stays exactly as it is. `PromptOneTap` and `CancelOneTapPrompt` are added to the same `domain/usecases/` directory, bound in `domain/domainModule.ts` the same way, with new `SIGN_IN_TOKENS` entries in `tokens.ts`. `SignInRepository` (the domain port) gains two methods — `promptOneTap(): Promise<void>` and `cancelOneTapPrompt(): void` — implemented on `BetterAuthSignInRepository` beside `mountGoogleSignInButton`. `cancelOneTapPrompt` reports nothing back; `promptOneTap`'s resolution is not a sign-in report (that is still the same `$sessionSignal` flip the button relies on) but the only signal that Google's own prompt lifecycle — display, retry backoff, eventual skip or dismiss — has settled, which the hook needs before asking again without colliding with better-auth's single-flight lock (see the retry note below). Every decision about *when* to call either use case lives in the hook, not the repository. Rejected: extending `MountGoogleSignInButton` with a mode flag — the two are different Google entry points with different lifecycles (a mounted DOM node vs. a fire-and-forget prompt), and a flag would make the button's simple case carry the prompt's state.

**Dismissal reaches past better-auth's wrapper.** better-auth's `oneTapClient` exposes exactly one action, `oneTap(opts) => Promise<void>` (`client.d.mts:167`) — no cancel handle, no cleanup function. The only way to interrupt an in-flight prompt is Google's own global, `window.google.accounts.id.cancel()`, reachable once better-auth's `loadGoogleScript()` has injected the GSI script (it sets `window.googleScriptInitialized`, not a wrapper around `window.google` itself). `cancelOneTapPrompt()` calls that global directly, guarded by `typeof window.google?.accounts?.id?.cancel === "function"` so a call before the script loads is a no-op rather than a throw. This is a deliberate, isolated escape past the library boundary, kept to this one method on `BetterAuthSignInRepository` — the same file that already reaches `window.google` indirectly through better-auth's client — rather than spreading a raw global reference through the domain or presentation layers.

**Suppression is component state on the hook, not `sessionStorage` or a repository flag.** The suppression is same-SPA-navigation only (`root.tsx` never hard-reloads between pages), and the hook that decides to call `promptOneTap()` is the same hook mounted once for the life of the app — so a `useRef` inside it (reset only by a real page reload, which is a legitimately fresh visit) is enough. No cross-tab or cross-reload persistence is asked for, so `sessionStorage` (the one precedent in the repo, `packages/grade10-store/frontend/src/core/analytics/trackProductAddedOnce.ts`, built for cross-reload dedup) would be reaching for more durability than the requirement calls for, and a repository-level flag would put UI-flow state in a layer that otherwise only wraps the client.

**One hook coordinates prompt, dialog and decline**, `useOneTapPrompt()` in `presentation/hooks/`, mounted once per app. It holds seven refs across two effects — `promptActive` (a call to `promptOneTap()` is outstanding), `interrupted` (the dialog opened while a prompt was active), `suppressed` (a decline has already happened this visit), `wasOpen` (the dialog's own open value as of the last run, to detect the transition), `requestPending` and `missedRequest` (the retry bookkeeping below), and `latest` (a ref mirror of this render's inputs, read by that retry once it fires after a later render):
- One watches `useSignInOverlay().open`. On `false → true` while `promptActive` is set, it calls `cancelOneTapPrompt()`, clears `promptActive`, and flips `interrupted` on. On `true → false` while `interrupted` is set and the visitor still has no session, it sets `suppressed` — the dialog's own close is the decline signal, not anything Google reports back. `interrupted` clears either way, so a dialog open/close that never caught a live prompt costs nothing.
- The other calls `promptOneTap()` whenever the brand offers Google, the visitor has no session, the dialog is not open, and `suppressed` is not set — re-checked on every dependency change the hook re-renders for. better-auth's `oneTap()` guards Google's own call with a single module-wide lock shared by every call site: a second ask while the first is still resolving — Google's own retry backoff can hold it open for tens of seconds — is silently dropped, no notification, nothing shown. `requestPending` tracks this hook's own outstanding call so eligibility regained mid-flight is remembered in `missedRequest` and asked for again once the first call settles, instead of colliding with that lock — landed after ship (commit `a6e4e8b9d`), once the single-flight lock's silent drop showed up in practice. `promptActive` clears in that same settle, not only via the two paths above: Google resolves `promptOneTap()`'s promise when the prompt ends on its own (ignored, skipped, not displayed), not only through a cancel — a gap that shipped and was caught and fixed after the fact (see Risks).

**The repository serializes its own two entry points against better-auth's shared lock — plumbing, not the hook's policy boundary.** `mountGoogleSignInButton()` and `promptOneTap()` are the only two callers of `client.oneTap()`. better-auth checks one module-wide lock on every call but only the auto-prompt branch holds it, so a button render arriving while a prompt is in flight is silently dropped — no notification, nothing shown, nothing retried. `promptOneTap()` now tracks its own call as `promptInFlight`; `mountGoogleSignInButton()`, finding one set, calls `cancelOneTapPrompt()` — releasing the lock along the immediate `cancel_called` path rather than waiting out the full retry backoff — and defers its render until that promise settles. "Every decision about *when* to call either use case lives in the hook, not the repository" still holds for policy: whether to show, suppress, or interrupt the prompt for a visitor is entirely the hook's. This is narrower — the repository keeping its own two calls to the one client it wraps from losing to each other — the same category of escape past the library boundary `cancelOneTapPrompt` already is, not a second decision-maker for the hook's gating. Shipped without it and caught after (see Risks): the durable `shared-auth-sign-in-SC-14` requires the Google control present whenever a person opens sign-in on a Google-enabled brand, with no carve-out for a corner prompt mid-flight, and this change's own suite never once exercised both entry points racing.

`onPromptNotification` is wired on the repository's `promptOneTap()` call, but only to `console.debug` the reason a prompt ended without a sign-in — diagnostics, not a decision input. Rejected, still: reading it to decide `suppressed` from a `dismissed`/`skipped` moment directly. It cannot tell "declined through the dialog" from "ignored and clicked away," and `shared-auth-sign-in-SC-88` requires the second case to cost nothing — wiring it into suppression would have penalized visitors who never interacted with sign-in at all. (Tracing better-auth's own source confirms this notification carries no timing advantage over the promise's own settle either: every branch calls `onPromptNotification` and resolves in the same synchronous step, so there is nothing left to gain by threading it through for `promptActive` specifically.)

**Library defaults stand.** `promptOptions.fedCM` stays on and `cancelOnTapOutside` is left unset — better-auth's own note says the two conflict. FedCM's own account chooser is browser-owned UI no page can recolor or brand, which the shipped prompt's dark chrome on this light-only product surfaced immediately; `decisions.md` Q6 is the author's word that this is an accepted limit, not a gap to code around.

**Mount point.** A new sibling component wrapping the hook (or the hook called directly from an existing chrome component, engineer's choice at implementation) sits inside `SignInOverlayProvider` beside `SignInDialog`: `apps/frontend/grade10/src/root.tsx` near `SignInBeforeNavigating` (~line 334) and `apps/frontend/zzz/src/root.tsx` near `SignInDialog` (~line 76). Each app's own `useSession()` and brand check are what it reads — no new context, no new provider.

## Risks / Trade-offs

- **[Risk]** A better-auth upgrade changes how the GSI script is loaded or shapes `window.google` differently → `cancelOneTapPrompt()`'s direct global call breaks silently. **Mitigation:** the guarded existence check makes a missing API a no-op, not a crash, and the call is isolated to one method for a future upgrade to update.
- **[Risk]** better-auth's built-in retry/backoff re-invokes `prompt()` after a decline, racing the suppression flag. **Mitigation:** the retry loop runs inside the one outstanding `oneTap()` promise, not as a second call from this code, so there is no second call site for it to race — `suppressed` only ever gates the hook's own next call, which the retry loop cannot trigger.
- **[Risk]** FedCM's account chooser cannot be recolored — a visitor on a dark browser sees dark chrome even on this light-only product. **Mitigation:** `color_scheme: light` styles the classic-iframe fallback for a browser without FedCM; the FedCM path itself is an accepted limit (`decisions.md` Q6), not a gap this change codes around.
- **[Shipped, caught, fixed]** `promptActive` cleared only on a cancel or on eligibility withdrawn — never on the prompt ending on its own (ignored, skipped, not displayed). A visitor who ignored the prompt once, then later opened and closed the sign-in dialog for an unrelated reason, was wrongly suppressed for the rest of the visit: the stale flag made that unrelated dialog close read as declining a still-showing prompt (`shared-auth-sign-in-SC-88`'s "costs nothing" contract, and `SC-90`'s own precondition that a prompt was genuinely showing when the dialog opened). Fixed by clearing `promptActive` in `promptOneTap()`'s `.finally()`, which fires on every way the promise settles, not only a cancel. `useOneTapPrompt.test.tsx` carries the regression case.
- **[Shipped, caught, fixed]** `mountGoogleSignInButton()` and `promptOneTap()` shared better-auth's one module-wide `oneTap()` lock with no coordination between them — a first-time visitor opening the sign-in dialog while the site's own corner prompt was still asking lost the Google button outright to the lock's silent drop, breaking the durable `shared-auth-sign-in-SC-14` ("the Google control is present" whenever a person opens sign-in on a Google-enabled brand). Fixed by having the repository serialize the two calls against its own tracked `promptInFlight` (see Decisions, above `onPromptNotification`). `BetterAuthSignInRepository.test.ts` and `apps/frontend/grade10`'s `OneTapPrompt.test.tsx` both carry the regression case.
