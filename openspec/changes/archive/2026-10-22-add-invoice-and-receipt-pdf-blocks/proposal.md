**Author:** @seankcw - 2026-09-23

## Why

`grade10-site/auction/winner-order` has required a viewable, downloadable
Invoice PDF and Receipt PDF since `winner-order-SC-57` and `winner-order-SC-67`
landed, and `docs/references/auction-invoice-and-receipt-contents.md` already
carries every line either document shows. No shared implementation renders
either one: `grade10` opens a hardcoded placeholder PDF today
(`PLACEHOLDER_RECEIPT_PDF`), and this repository's own preview carries only an
illustrative sketch composed straight from `@grade10/design-system`
primitives, explicitly flagged as "not a `packages/ui` block" pending its own
change. Every other reused surface on Winner Order — the order detail, the
address form — already lives once in `@grade10/ui`; the two documents are the
one place left where "one shared implementation, every consumer imports it" is
a claim this repository does not yet back with a component.

**Metric:** the number of independent implementations of the Invoice and
Receipt PDFs — two once groups 1-2 landed here (this repository's DOM
component, never adopted, and `grade10`'s own pdf-lib renderer, which shipped
to production regardless and already replaced `PLACEHOLDER_RECEIPT_PDF`
there). This amendment (`decisions.md` Q18) collapses that back to one by
moving `grade10`'s renderer into `@grade10/ui` and retiring the DOM component;
the count reaches one real, shared implementation once this lands, and zero
consumers outside `@grade10/ui` once `grade10` switches its import (`grade10`'s
own task, see Impact).

## What Changes

- **Amendment (`decisions.md` Q31-Q39): items as rows.** `InvoicePdf` and
  `ReceiptPdf` list an order's items as table rows, each with Winning Bid,
  Buyer's Premium and Total, on every document including one with a single
  item. The Item Total row, the charges under the table and the summary
  follow it, and a table too long for one page continues on the next. This
  replaces the lot heading and the Description/Amount header the Q18-Q20
  amendment below describes, and changes the one-A4-page rule to one page per
  fitting table. Each invoice still holds one lot; combining lots is not part
  of this change.
- **Timezone alignment:** PR #921 fixes invoice and receipt PDF dates to
  `Asia/Hong_Kong`, labelled `GMT+8`. This amendment removes the proposed
  winner-selected zone, phone entry, invoice snapshot and `winnerTimeZone`
  renderer input. Collector screens continue to use the viewer's local zone.
- **Amendment (`decisions.md` Q18-Q20): the DOM component is retired and
  replaced by `grade10`'s pdf-lib renderer.** `shared/ui/invoice-and-receipt-pdf`
  still exports `InvoicePdf`/`ReceiptPdf`, but each is now a function that
  takes a plain data object and an optional embedded-font override and
  returns the document's PDF bytes, not a React component:
  - `InvoicePdf` draws the invoice's title and issuer mark, meta rows
    (invoice number, sent-at and payment-deadline dates, and payment method),
    Bill To and Ship To, including a phone line when supplied, the lot
    heading, a Description/Amount table of charges ending in a
    Subtotal/Payment Processing Fee/Order Total summary, an optional supplied
    `taxLine`, an optional plain-text `Replaces invoice {id}` row, and the issuer block pinned to the sheet's bottom right.
  - `ReceiptPdf` draws the same title/issuer-mark, meta rows (receipt number,
    the invoice number it pays, date paid, payment method, payment
    reference), Bill To and Ship To, including a phone line when supplied, the
    same lot/charges/summary table, an optional supplied `taxLine`, an
    optional transfer-reference line, the four-line payment breakdown
    (Original Invoice Total, Previous Payments, Current Payment Received,
    Remaining Balance Due), and the same issuer block.
  - Every amount arrives pre-formatted and every date as a `Date`. Every
    label routes through a `copy` argument added for this move (Q20), never
    hardcoded in the package.
- **Retired as non-goals (`decisions.md` Q19):** receipt status badges, the
  manually-settled mark, the Superseded invoice treatment, and
  `issuerTaxDetails`. The existing optional `taxLine` slot remains part of the
  PDF contract because `add-winner-order-tax-line` already depends on it; it is
  a plain caller-supplied `PdfLineItem`, not a React node.
- **Every story that rendered `InvoicePdf`/`ReceiptPdf` as JSX moves to
  previewing generated bytes instead**, since there is no component left to
  render: the block's own colocated
  `invoice-pdf.stories.tsx`/`receipt-pdf.stories.tsx`, and `apps/preview`'s
  `winner-order.invoice-pdf.stories.tsx`/`winner-order.receipt-pdf.stories.tsx`
  (which group 2.4 had already pointed at the DOM component). Each calls the
  renderer on sample data and previews the resulting PDF with a small
  `pdfjs-dist`-based canvas viewer (`pdf-preview.tsx`).

## Scope boundaries

- **Tax line shape.** This change exposes the presentation slot only: an
  optional `PdfLineItem` named `taxLine`, supplied by the application and
  rendered on both documents before the summary. Tax calculation,
  jurisdiction and persistence remain owned by the auction tax change.
- **Formal tax receipt.** This change exposes no company-details or tax-ID
  receipt block. Finance may sponsor a future requirement when one exists.
- **Bank account details.** `InvoicePdf` receives the immutable payment-
  instruction snapshot issued by Finance configuration. Live SWIFT, FPS and
  Hong Kong local values, including the QR asset, are not source-controlled.
- **One lot per invoice.** `winner-order` still requires one invoice and one
  auction order per lot. The item table draws what the application supplies and
  decides nothing about how many lots an invoice holds (`decisions.md` Q31).
- **Stored PDFs.** The archive serves the bytes of a document's first open, so
  an invoice or receipt opened before this ships keeps its old layout
  (`decisions.md` Q37).
- **Refusals.** A document the renderer cannot draw whole - no items, a title
  the standard font cannot draw, a row or amount set that cannot fit - is
  refused, not drawn cut or shrunk (`decisions.md` Q38, Q39).
- **Replacement relationship.** The active
  `define-public-auction-identifiers` delta is kept in the same direction as
  this contract: the new invoice carries `replacesInvoice` and renders
  `Replaces invoice {id}`. The prior invoice remains retained and does not
  become cancelled merely because it was replaced.
