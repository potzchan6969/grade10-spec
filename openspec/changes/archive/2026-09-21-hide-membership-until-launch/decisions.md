## Goals

- A collector on preview or production finds `/membership` and `/join`
  answering not-found, the same as the store, the vault, booking and the
  profile already do
- A collector on development or staging sees both pages exactly as they do
  today
- Reopening membership is one reviewed line, the same shape as opening any
  other waiting product

## Non-Goals

- Deciding when the loyalty programme finishes, or reopening the gate - a
  follow-on change, once it is ready
- Retiring `/join` in code - a separate, not-yet-scheduled change; gating it
  now neither blocks nor duplicates that removal
- `/bids`, sign-in, or any other loyalty-adjacent surface - untouched
- Any change to the loyalty programme's own content or behavior - this
  change only decides which lanes carry the two pages
- The operator console - unaffected; it already decides its own surfaces per
  lane

## Decisions

| Q | Asked | Decided | Instead of |
| --- | --- | --- | --- |
| Q1 | Why gate `/membership` and `/join` now, when the carried-surfaces PRD explicitly decided the loyalty pages stay carried everywhere? | The loyalty programme is mid-build: the wallet card's issuer credentials are recorded pending for both platforms, the member card renders an honest "not switched on" for a brand with no minter gateway configured, expiry reminders are recorded with no channel yet built to tell a member, and `/join` itself is a standing removal the code has not caught up with. It waits like the store, the vault and booking did before their own launch, and reopens the same way once the programme is ready. Reverses a running decision - **BREAKING**, recorded on the PRD. | Leaving the PRD's "the loyalty pages stay" decision standing and shipping the gate as an undocumented exception - the next reader would read the PRD as still true. |
| Q2 | Which lanes carry it? | (recommended) The same mechanism as the store, the vault and booking: `gatesFor` keys on the deploy environment, open wherever it is not `"production"`. Preview shares `deployEnv: "production"` with production itself, so this reads as "carried in development and staging, shut in preview and production" - exactly what was asked for, with no new gate shape. | A gate keyed on the site stage instead, already rejected for every other waiting product for the same reason: the stage reads `preview` for production by one registry row. |
| Q3 | `/membership` and `/join` link to each other (`JoinPage.tsx` links to `ROUTES.membership`, `MembershipPage.tsx` links to `ROUTES.join`). Does either link need to hide itself the way the profile change's in-app links did? | No. Both surfaces carry the same gate, so a build either carries both or neither - there is no reachable state where a collector is on one page while the other is withheld. This is a genuine divergence from the profile change: its in-app links pointed at a surface with its own independent gate, so hiding them mattered. | Adding a `carries("membership")` guard to both links anyway, for symmetry with the profile change. Rejected: it is dead code on every build this table can produce, and the carried-surfaces rule only asks that nothing name an absent surface - neither link ever does. |
| Q4 | `src/serving/pushNotification.ts` builds a spend notification addressed at `ROUTES.membership` with no gate check at all - none of the store's, the vault's or booking's gates had to solve this, since nothing there sends a notification to a withheld surface. What happens to it here? | No code change. A spend notification fires only after a points spend at checkout, which already requires the `store` gate; `store` and the new `membership` gate read the identical `deployEnv !== "production"` line, so on every lane this table can produce, a build able to generate the event also carries the page the notification points at. Recorded here rather than silently assumed, since the two gates are only accidentally identical today - a future change that diverges them would need to revisit this. | Gating the notification's address on `config.gates.membership` regardless. Rejected as unneeded defensive code against a state no lane can reach today; revisit if `store` and `membership` ever move independently. |
| Q5 | Do `/membership` and `/join` name any nested address, the way `/profile/orders` sits under `/profile`? | No. `apps/frontend/grade10/src/surfaces.ts`'s `SURFACES` table lists no address beneath either. | Writing a speculative case for an address that does not exist. |
| Q6 | `hide-profile-until-launch` sits in this same store, in this same capability, with its `tasks.md` fully checked off and its PRD already reading as shipped - but the durable `openspec/specs/grade10-site/site/carried-surfaces/spec.md` has never been folded to include it, and `pnpm run archive:preflight hide-profile-until-launch` refuses on missing deploy evidence (the repository's `Deploy` workflow has been failing at a database-migration check since 2026-09-18, before the profile-gate PRs even merged). Does this change wait on that one, or fold membership on top of it? | Neither. This change is written as its own delta against the durable spec.md exactly as it stands today - three waiting products (store, vault, booking) - and names no dependency on the profile's still-open delta. Whichever of the two changes actually ships and archives first fixes up the requirement text for the one archiving second; that is an ordinary concurrent-delta resolution at archive time, not a blocker for writing either change now. | Blocking this change on `hide-profile-until-launch` archiving first, or silently writing this delta as though the profile's were already folded (the PRD's own premature unmarking of the profile row invites exactly that mistake). Both rejected: the PRD's decided-not-🚧 model already flags the same failure mode - "an unmarked line and the spec disagree, the spec is right about what runs." |
| Q7 | The blind suite pass asked whether the crawler/chrome requirement needs a membership-specific scenario, having drafted cases extending the preview-host, sitemap and robots.txt checks to name `/membership` and `/join`. | No. `/membership` and `/join` are `kind: "session"` surfaces in `apps/frontend/grade10/src/surfaces.ts`, never members of `PUBLIC_SURFACES` (only `prerendered`/`rendered` surfaces are) - so neither address was ever named in a sitemap, robots.txt, the header, the footer or the front door, gated or not. Confirmed by precedent: the durable suite's own existing crawler/chrome cases never name the profile either, for the identical reason. | Folding the drafted cases in anyway for symmetry with the store/vault/booking crawler cases - rejected as testing a claim that was never true for any session-kind surface, membership included. |
| Q8 | The blind suite pass asked whether `/join`'s standing, not-yet-scheduled removal (the `@ecchochan` callout) could produce a third state - a removal notice, rather than "answers" or "404" - on a lane that still carries membership. | Out of scope for this change. Retiring `/join` in code is already a listed non-goal and a named follow-on change; whichever change lands first is free to adjust the other's assumptions when it does. This change's own scenarios describe only the two states `/join` has today. | Speculating about the removal change's shape now, or blocking this change on it being scheduled first - rejected as scope creep into a change that does not exist yet. |
| Q9 | The blind suite pass asked whether a collector already holding loyalty state (a points balance, a provisioned wallet card) is tested differently at `/membership` than one with none, the way `US6-TC4-1` tests a signed-in collector who already holds a vault case or a booked visit. | No case owed here. Carried surfaces owns only whether an address exists and answers; what a member with a balance sees once the address is carried is `grade10-site/loyalty/programme`'s own behaviour, already covered by that capability's suite. | Adding a membership-state row to this capability's withheld/carried test data for parity with the vault and booking rows - rejected because those rows exist to prove a mailed link or an existing record still resolves through the *store's* gate (Q3 in the profile change's own decisions), a question that does not arise here since membership has no nested address (Q5) and no other capability's gate to interact with. |
