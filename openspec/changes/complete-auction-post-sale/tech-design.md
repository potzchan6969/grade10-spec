## Overview

**Winner** - wins, opens the order from the `auction_won` letter, completes setup once (delivery address, payment method, billing address) on the site as it stands, waits for the invoice, pays by card through Stripe Checkout or transfers and submits the proof, gets a receipt, then sees the lot shipped and delivered.

**Operator** - opens the Orders worklist, sends the invoice (shipping, insurance, tax, processing fee pre-filled from the fee schedule), reissues it when something changes, records bank money or checks the winner's proof, dispatches, confirms delivery, and cancels, refunds or comments when needed.

**Architecture** - `@grade10/auction-contracts` holds the pure rules (pricing, status, actions, segments, payment outcome) that the backend enforces and both clients render; the auction worker's `services/orders/*` own every transition under the order row lock; the order's status is never stored - one SQL `CASE` in the worklist repository mirrors the contracts rule over fact columns; the storefront reaches the auction through a winner-only RPC entrypoint; the admin console is a thin client of one read model, `OperatorOrderView`; the winner's site keeps its design and its procedures, and this change's rules hold behind them.

```
Payment Settings (minimum premium, card rule, bank rule)    Send / Reissue dialog (shipping, insurance, tax, fee)
                                  \                        /
                 contracts/invoicePricing.priceInvoice(lines)
                   subtotal = hammer + premium + shipping + insurance + tax;  total = subtotal + processingFee
                                  |
        dialog preview <----------+-----------> sendInvoice / reissueInvoice: prices again under the lock,
        expectedTotalMinor                      refuses QUOTE_CHANGED, then insertInvoiceRevision (the one
                                                writer of auction_invoices; current_invoice_id moves;
                                                letter invoice_sent; reminders anchored to the deadline)
```

```
card   site Pay with Card -> store RPC payWinnerInvoice -> auction prepareCheckout (fresh session every time)
         -> Stripe Checkout (card only, expires_at, metadata { orderId, invoiceId })
         -> webhook completed | async_payment_succeeded -> recordCheckoutPaid(session)
              money is always written; an invoice that cannot take it flags the payment row
         -> webhook expired | async_payment_failed -> recordCheckoutClosed(sessionId)

bank   winner uploadWinnerPaymentProof(files) -> payment_verifying -> operator Check proof -> paid
       operator recordPayment (bank transfer) -> partially_paid | paid | paid + overpaid flag
```

## Data Model

Every migration is expand-only, generated by `pnpm run db:drizzle:generate` and checked by `pnpm run check:migrations`. Backfills are plain `UPDATE` statements in the same migration and carry `-- lock:` where the check asks; a widened check constraint is `DROP` + `ADD`, added valid with a `-- lock:` note, because drizzle runs a migration in one transaction and `NOT VALID` + `VALIDATE` in it would hold the same lock. Nothing is dropped; columns the code stops reading are listed under `-- contract:`. The fee columns are auction `0006`, shipped with the fee schedule; the order columns are `0007`; the command ledger, staged proofs and the log's new columns are `0008`, all under `apps/backend/grade10/auction/src/db/migrations/`.

### Derived Status

The status is a function of facts, read where it is needed and stored nowhere. `deriveAuctionOrderStatus(facts)` in contracts is the rule; `orderStatusSql(now)` in `repositories/orderQueue.ts` is one `CASE` the worklist, the counts and the detail share:

```sql
SELECT o.id,
  CASE
    WHEN i.status = 'refunded' THEN 'Refunded'
    WHEN o.cancelled_at IS NOT NULL OR i.status = 'cancelled' THEN 'Cancelled'
    WHEN i.status = 'paid' AND o.delivered_at IS NOT NULL THEN 'Delivered'
    WHEN i.status = 'paid' AND o.dispatched_at IS NOT NULL THEN 'Shipped'
    WHEN i.status = 'paid' THEN 'Processing'
    WHEN i.status = 'partially_paid' THEN 'Partially Paid'
    WHEN i.status = 'payment_verifying' THEN 'Payment Verifying'
    WHEN i.status = 'expired' THEN 'Payment Overdue'
    WHEN i.status = 'pending' THEN 'Pending Payment'
    WHEN o.delivery_address_confirmed_at IS NOT NULL THEN 'Preparing Invoice'
    WHEN o.address_deadline_at <= $now THEN 'Setup Overdue'
    ELSE 'Awaiting Setup'
  END AS status
FROM auction_orders o
LEFT JOIN auction_invoices i ON i.id = o.current_invoice_id
```

- **Current invoice** - `current_invoice_id` is the pointer every reader and sweep uses; a revision that is not the pointer is replaced, and "replaced by" is the row whose `supersedes_invoice_id` names it
- **Cancelled** - reads from `cancelled_at` or the current invoice's `cancelled` status. A cancel sets both when the order has an invoice and only `cancelled_at` when it has none, so the order-status machine keeps its `cancelled` invoice status and no synthetic invoice is written; production's existing synthetic cancelled revisions read right without a backfill
- **Setup confirmed** - one stamp, `delivery_address_confirmed_at`, in SQL and in TypeScript
- **Since** - a second `CASE` over the same rows gives the stamp that moved the order into its status: `created_at`, `address_deadline_at`, `delivery_address_confirmed_at`, `i.sent_at`, `i.payment_deadline`, the last payment's `created_at`, the last proof's `created_at`, `i.paid_at`, `dispatched_at`, `delivered_at`, `cancelled_at`, the refund's `created_at`; a flagged order reads the flagged payment's `created_at`
- **Flagged** - `EXISTS` a payment row on the order with `flag IS NOT NULL AND flag_cleared_at IS NULL`
- **Balance** - the sum of payment rows that count toward the current invoice: every row on it except one flagged `amount_mismatch`. Money on a replaced or cancelled invoice counts toward nothing
- **Matrix test** - `packages/grade10-auction/backend/test/repositories/orderQueue.repo.test.ts` seeds every combination of invoice status, `cancelled_at`, `dispatched_at`, `delivered_at`, `delivery_address_confirmed_at` and deadline against `now`, and asserts the SQL status and since equal the TypeScript ones
- **No sweep for setup** - Setup Overdue is time in the rule; the `setup_overdue` letter is queued at close. The `expiredInvoices` sweep keeps writing `expired` on the current invoice past its deadline and suspends the bidder in the same transaction; the `suspendedBidders` list goes. A cancelled order is skipped by the sweep
- **A payment started in time counts** - the sweep leaves a `pending` invoice alone while its checkout session is open, which is at most 30 minutes past the deadline; `recordCheckoutClosed` writes `expired` at once when the deadline has passed, as `close-overdue-address-confirmation` asks

| Segment | Statuses |
| --- | --- |

A flagged order sits only in Needs action, so the counts add up to All. The rules module is the only place an action's precondition is written: every mutation loads facts under the lock and refuses with `operatorRefusal`; grants stay outside it, the router enforces them and the console renders them.

Rules `operatorRefusal` holds beyond the status table:

- **recordPayment** - only a bank transfer invoice in `pending`, `expired` or `partially_paid`; a card invoice paid by transfer is reissued as bank transfer first
- **reissueInvoice** - `pending` or `expired`, no payment that counts toward the balance, no proof under review; `deadline: kept` refused on `expired`
- **cancel** - Awaiting Setup, Setup Overdue, Preparing Invoice or Payment Overdue, before any payment that counts toward the balance (`ORDER_HAS_PAYMENTS`) and with no proof under review (`PROOF_UNDER_REVIEW`); a pending invoice is left to expire or is reissued
- **refund** - `paid` or `partially_paid`, no refund yet; the basis is every payment that counts toward the balance; a refund of exactly the overpayment keeps the status
- **dispatch** - paid and not dispatched; **confirmDelivery** - dispatched (`NOT_DISPATCHED`) and not delivered

### Refusal Codes

Codes travel as values (`{ success: false, errorCode }`) through every layer; a sentence is made once, in the last layer: `refusalCopy.ts` in the admin slice; the site's sentences come from the catalogs. `auctionRefusalCodes` loses `PAYMENT_FEES_UNREADABLE` and gains:

| Code | Refuses |
| --- | --- |
| `QUOTE_CHANGED` | a send or reissue whose `expectedTotalMinor` differs from the server's pricing; no payload, the dialog refetches and prices again |
| `NO_CHANGE` | a reissue that changes nothing |
| `METHOD_UNAVAILABLE` | bank transfer where the lane has no bank details for the currency |
| `PROOF_UNDER_REVIEW` | cancel, reissue or a second submit while a proof waits |
| `ORDER_HAS_PAYMENTS` | cancel after money was recorded |
| `NOT_DISPATCHED` | delivery before dispatch |
| `ACCOUNT_EXISTS` | a test winner at an address that already holds a verified account |

`WINNER_REFUSAL_CODES` names what a winner procedure can return: `NOT_FOUND`, `ADDRESS_LOCKED`, `ADDRESS_WINDOW_CLOSED`, `METHOD_UNAVAILABLE`, `ORDER_NOT_PAYABLE`, `DEADLINE_ELAPSED`, `INVOICE_EXPIRED`, `PROOF_INVALID`, `PROOF_UNDER_REVIEW`, `UNAVAILABLE`. The site answers every code in `WINNER_REFUSAL_CODES` from the shared catalogs, `auctionOrders.refusal.<code>` in `en`, `zh-Hant`, `zh-Hans` and `ko`, and a missing key fails the build. `refusalMessage` reads the catalog in place of its own map, and a code outside the list reads as the catalog's generic refusal, `auctionOrders.refusal.generic`, never showing the code. Every other code is the console's alone.

## Key Flows

Every post-sale mutation, setup confirm included, locks the order row and reads `now` after the lock; no post-sale path locks the listing.

### Setup Confirm (winner)

1. Store router forwards `confirmWinnerAddress` with the session's `userId`, as today
2. `confirmSetup` locks the order, loads facts, requires `completeSetup` in `winnerActions` (`ADDRESS_LOCKED` once confirmed, `ADDRESS_WINDOW_CLOSED` past the deadline)
3. Bank transfer is refused with `METHOD_UNAVAILABLE` unless `bankDetailsFor` answers for the lot's currency
4. Writes the delivery and billing snapshots and the method, `delivery_address_confirmed_at`, log `address_confirmed`; parks the setup letters. The choices are locked: only an operator changes them after, and `amendWinnerOrderAddress` answers `ADDRESS_LOCKED`

### Send

1. The dialog prices with `priceInvoice` and shows the total; submit carries `expectedTotalMinor`
2. `sendInvoice` locks, requires no refusal, replays on `(orderId, idempotencyKey)`
3. Prices again from the lock: hammer, `buyerPremiumMinor(hammer, settings.minimum)`, the four inputs; a different total answers `QUOTE_CHANGED`
4. `insertInvoiceRevision` writes revision 1 with `payment_method` from the order, `payment_deadline = now + 7 days` to the minute, `sent_at`; moves `current_invoice_id`; log `sent`; letter `invoice_sent`; reminders anchored to the deadline at distinct instants (day 3, day 6, 24 h before)

### Reissue

1. Allowed on `pending` or `expired` with no payment that counts toward the balance and no proof under review
2. Needs a reason and at least one changed field (`NO_CHANGE`); prices as Send does; `deadline: kept` keeps the instant and its reminders, `reset` is `now + 7 days`
3. `insertInvoiceRevision` writes revision n+1 with `supersedes_invoice_id`; the old revision is left as it is; `current_invoice_id` moves; the order's setup snapshots take the new address or method; any open checkout session is expired at Stripe; log `reissued`; letter `invoice_sent`

### Card Payment

1. `payWinnerInvoice` runs `prepareCheckout`, which requires `payByCard`; under the lock reads `checkout_attempts = n` and the stored session
2. Outside the lock: expires the stored session at Stripe when one is open (a completed one is recorded by its webhook); creates a session with idempotency key `checkout:<invoiceId>:<n+1>`, `payment_method_types: ["card"]`, `expires_at = clamp(paymentDeadline, now + 30 min, now + 24 h)`, metadata `{ orderId, invoiceId }`
3. Under the lock: `UPDATE ... SET checkout_session_id, checkout_expires_at, checkout_attempts = n + 1 WHERE checkout_attempts = n`; a click that loses the set answers the stored session
4. `checkout.session.completed` and `async_payment_succeeded` run `recordCheckoutPaid(session)`: the invoice comes from `metadata`; after the Stripe reads succeed nothing throws; the payment row is keyed `checkout:<sessionId>`, so a replay changes nothing

| When the money lands (the first row that fits) | Result |
| --- | --- |
| order or invoice unknown | 200, counted and logged with the reason |
| order cancelled | recorded + flag `paid_after_cancel`; counts toward nothing |
| not the current invoice | recorded + flag `paid_replaced`; counts toward nothing |
| amount or currency differs | recorded + flag `amount_mismatch`; counts toward nothing |
| `pending` | paid |
| `expired` | paid + flag `paid_late` (the operator's cue to lift the suspension) |
| `paid`, another session | recorded + flag `overpaid` |
| any other status | recorded + flag `unexpected_status`; counts toward nothing. Only a card invoice opens a session, and only a bank transfer invoice reaches `payment_verifying` or `partially_paid`, so this row is the backstop |

Money that counts toward nothing never blocks a reissue or a cancel. Finance returns it outside Grade10, and an operator clears the flag with a reason. An expired or verifying invoice never starts a card payment; one that completes anyway lands by this table, and only `expired` moves, to `paid`, as the modified order-status transitions allow.

5. A paid transition sets `paid_at`, writes the `paid` log row (brand, last four), sends `payment_received`, parks the reminders; a flag writes `payment_unexpected`
6. `checkout.session.expired` and `async_payment_failed` run `recordCheckoutClosed(sessionId)`: clears the pointer only while it still names that session; log `payment_attempt_failed`
7. Return: the site's return page is unchanged, and the webhook alone records the payment

### Proof

1. Winner: `uploadWinnerPaymentProof` takes the files as today; the server judges each by its content, not its name or declared type, and refuses one that is not PDF, PNG, JPEG, HEIC or HEIF; HEIC and HEIF are stored only once converted to JPEG, and HEIC or HEIF bytes that arrive unconverted are refused, where `winnerPaymentProof.ts` today labels them `image/jpeg` as they are; keys `proofs/<sha256>.<ext>`; invoice -> `payment_verifying`, `payment_time_left_ms` frozen, reminders parked. An object stored before a failure is reclaimed by the orphan sweep after a day
2. Operator return: external reason (the winner reads it) and internal note; invoice -> `pending`, `payment_deadline = now + timeLeft`, reminders resume; letter Proof not accepted
3. Operator confirm: payment row `bank_transfer` for the invoice total, log `proof_confirmed` then `paid`; letter `payment_received`
4. Operator upload: `PUT .../proofs?kind=` returns the key for `recordPayment`, `recordRefund` or `confirmDelivery`; the `GET` serves any kind `inline` with the sniffed type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, `Cache-Control: no-store`, audited, and only a key the order's union names

### Operator Payment

1. `recordPayment` requires no refusal; the dialog pre-fills the balance; `paymentOutcome` drives the inline choice - close at 90 % or more or keep open, confirm an overpayment - and backs the server check (`PAYMENT_NEEDS_DECISION`, `PAYMENT_TOO_LARGE`)
2. Writes the payment row with `received_at`, the reason, the receipt snapshot, the proof keys; balance reached -> `paid` and `payment_received`; otherwise `partially_paid` and `payment_received_partial`; overpaid -> `paid` + flag `overpaid`

### Cancel

1. Requires no refusal; writes `cancelled_at`, `cancelled_by`, category, note and consequences, and sets the current invoice, when there is one, to `cancelled`
2. Expires any open checkout session at Stripe; releases the inventory hold and leaves the listing `closed`; parks the reminders; log `cancelled`; letter `order_cancelled`

### Refund

1. Requires no refusal; writes the refund with `refunded_at`, the structured destination, proofs; `return_to_stock` releases the hold and leaves the listing `closed`
2. A refund of exactly the overpayment keeps the invoice `paid`; any other refund sets it `refunded`; log `refunded`

### Dispatch and Delivery

1. `recordDispatch` writes the `fulfilment_log` row `dispatched` (carrier, tracking, tracker link, address snapshot) and `dispatched_at`; letter `shipped`
2. `confirmDelivery` writes `delivery_confirmed` with `delivery_at` and `delivery_proof`, and `delivered_at`; letter `delivered`

### Comment and Flags

1. `addComment` writes the row under the actor; it never changes the status and appears in the timeline
2. `clearPaymentFlag(paymentId, reason)` stamps the three cleared columns; log `payment_flag_cleared`; the order leaves Needs action once no flag is open

### Test Winner

1. `testWinners.create` runs on the `testBids` middleware; the email must be a plus-tag of the session's own address (default `<local>+qa-<code>@<domain>`), else refused
2. `AUTH_SERVICE.createUnverifiedAccount(email)` answers the account id; a verified account answers none and the create refuses `ACCOUNT_EXISTS`
3. `ensureTestBidder` (the test-mode Stripe customer) before the transaction
4. One transaction: upsert `auction_test_accounts` (the row lock serializes repeats); return the account's existing order on a sandbox lot when one exists; else `insertClosedSandboxLot` (published, `sandbox`, no campaign, title `Test lot <code>`, `ends_at = closedAt ?? now`, one `top` bid at the asked amount) and `closeOne(tx, listing, closedAt ?? now)`, which issues the order and queues `auction_won`, `setup_reminder`, `setup_overdue`
5. The console then sends the ordinary magic link: `signIn.magicLink({ email, callbackURL: <site>/auction/order?orderId= })`; the row offers it again. The letters and the sign-in mail reach the operator's own inbox; the link opens in a private window
6. `testWinners.list` answers the orders of registered test accounts on sandbox lots, newest first. Cancel is the ordinary order cancel; the lot lists among sandbox lots on non-production lanes and is never biddable
