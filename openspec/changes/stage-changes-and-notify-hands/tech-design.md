Drawn from [Change Stages](../../docs/prds/products/shared/planning/change-stages.md), the proposal and the journeys, before the requirements (decisions Q10). The requirements pass reads it; the reconciliation re-reads it.

## Context

- **Everything is derived today, and stays so.** `laneOf` in `tools/manual/src/api/derive.ts` reads four lanes from `deltas`, `taskGroups` and the tick counts; `pendingByTeammate` reads what each role owes from the schema's `teammate` and `requires`; `ChangeEntry` in `tools/manual/src/api/types.ts` already carries `owners`, `promotedBy`, `awaiting`, `dependsOn`, `deployedEnv`, `lastMoved` and `written`; each change document carries `lastCommit` from `git.commitOf`.
- **One record per change.** `.openspec.yaml` is read by `read-changes.mts` and checked by `tools/manual/check/record.mjs`; every waiver is text, never `true`, and a key read as absent waives nothing.
- **One post per push.** `.github/workflows/proposal-notify.yml` runs `scripts/openspec/changed-changes.mjs` on every push to `main`, on a full checkout, classifies the changes touched, and posts one channel message through `slackapi/slack-github-action`; its `paths:` filter omits `docs/prds/**`, it installs no Node toolchain, and it reads `github.event.before` for the base.
- **The board commits from the application repository.** `pnpm plan claim` and `pnpm plan done` in `grade10` push one commit each to this store's `main`, so a hand written from there follows the same path.
- **Git dates lie about idle.** `lastMoved` is the last commit touching the directory; the repository-wide commit of 2026-09-16 moved every change at once.
- **The checks run on a one-commit checkout.** `lint.yml` runs `check:manual` after a push to `main` at the default depth, so a rule there cannot read history and cannot refuse a landing.

## Goals / Non-Goals

**Goals:**

- One derivation of the stage, the hand and the hand's move, in `api/stages.ts`, that every surface and the notify workflow call
- The hands and who landed each artifact as the only stored facts this change writes, validated against the team map
- A direct message per hand change, and one per artifact going behind, that cannot be sent twice for one move

**Non-Goals:**

- Writing the read record, refusing a landing, or waking an agent: `run-a-round-on-every-artifact`
- A sign-in on the hosted manual
- A button on the messages this change sends; every message links the thread and the change page and carries the command as text. The one button a round's summary carries is the round change's (its decisions row Q90)
- Reading tags or deploys out of `grade10`; the store reads only what `pnpm plan` writes into it

## Decisions

The page governs what a stage is and who is told; these are how that lands.

- **Stage is a pure function of the entry.** `stageOf(change: ChangeEntry, artifacts: SchemaArtifact[]): Stage` in `api/stages.ts` - its own module beside `waivers.ts`, so the store's reader and the workflow script can read it under plain node where `derive.ts` cannot go - returning one of `proposed | designed | specified | planned | building | on-staging | released | archived`, computed in `read-changes.mts` where the schema is at hand and carried on the entry, and tested in `change-stages.test.ts` with one fixture per stage and one per boundary. `laneOf` becomes a projection of `stageOf` so the four lanes and the eight stages can never disagree while both exist. Rejected: a second reader in the workflow script, which would drift from the manual's within a week.
- **The hand is derived beside the stage.** `handOf(change, stage, artifacts): Role[]` returns whose turn it is: inside Proposed, `pm` until `decisions.md` and the journeys file are settled and `hands:` names every role the next stage needs - `design` unless `ui_waived`, `tech` unless `design_waived` - then those hands (Q49); `pm` at Specified; `dev` at Planned and Building; `qa` and `release` at On staging. Settled is the ladder's own predicate, `written ∪ waivedOf`, which is why it takes the artifacts: the stage and the turn cannot disagree about whether an artifact is in. A move is the pair `(stage, hands)` changing, which is what the workflow compares and what My turn lists. Rejected: a stage of its own for the completed proposal, which the page's decisions rule out.
- **The agent mark and the move are a table, not a key.** `DRAFTED: Partial<Record<Stage, { draft: string; moves: Partial<Record<Role, { move: string; command: string }>> }>>` for the five stages from `proposed` to `building` - answer, tweak and challenge, read, read, read each landing - beside `stageOf`, with a move and a command per hand of the stage, because Designed names two and each drafts one design (Q47). `draftedOf(stage, id)` in `api/stage-view.ts` is the one reader: the lane heading and the stepper join the moves, and the Your turn card and a card's next action name each hand and offer its own command. Partial, not total: On staging, Released and Archived carry no entry, and a lookup that misses is the three stages that carry neither mark nor move. Nothing in a change's record says it, because which stages an agent drafts is the schema's rule, not one change's.
- **A waiver is its own fact, beside what is written.** `waivedOf(artifacts, entry): Set<ArtifactId>` in `api/waivers.ts` maps `ui_waived` to `ui-design` and `design_waived` to `tech-design`; `written` keeps its meaning of a file that exists, so nothing that counts files sees a waiver as one. `stageOf` reads `written ∪ waivedOf`, the change page shows a waived artifact as not owed and fresh, and the `awaiting` rule in `record.mjs` gains one refusal: a record that waives an artifact and writes a wait on the same artifact is refused, naming the artifact and the line that waived it - `skip_specs` among them, which is why the pair's own branch is gone. Rejected: counting a waived design as written, which makes today's `ui_waived` plus `awaiting: ui-design` records newly refused with no migration to offer them.
- **The schema holds the order and the upstream set.** The schema's `requires` for `tech-design` becomes `decisions` and `user-journeys`, and `tech-design` moves above `specs` (decisions Q10); each artifact gains `upstream: [<ids>]`, the artifacts its text is drawn from, because the graph is not the artifact list's order - `feature-tcs` is blind to `spec`, and `tech-design` is not drawn from `ui-design`. `read-schema.mts` carries `upstream` on each artifact and refuses an id the schema issues nowhere in either list, `upstreamOf` reads it, and `shared/planning/agent-rounds` states the set; nothing here restates it. Each artifact also carries `hand:` - the role that answers for it - beside `teammate`, which cannot answer it: the tech design and the task list are both the engineer's there, while the hand of one is the tech PIC and of the other whoever builds it.
- **Hands are a mapping, not a list.** `hands:` maps `pm | design | tech | qa | dev | release` to one handle each; `read-changes.mts` parses it with the `handles` helper that already reads `owner`, and `record.mjs` gains a `hands` rule refusing an unknown role, a handle absent from the team map, and a value that is not one handle. `owners` keeps its meaning of who claimed work. Rejected: extending `owners` with roles, which would break `pnpm plan claim`'s reading of it.
- **Who landed an artifact is a key.** `landed_by:` maps a schema artifact id to the handle whose word landed it, written by the landing - `pnpm run plan:land`, or the person's own push through it - in the same commit as the artifact; `read-changes.mts` reads it beside `written`, `record.mjs` refuses a handle the team map does not know and an artifact id the schema does not issue, and the change page shows the handle beside the artifact. Replaces `plan_approved:` and `pnpm plan approve`: an artifact on `main` is an approved one (decisions Q14). Rejected: a commit trailer, which no reader in this store or in `grade10`'s `plan.mjs` parses.
- **One hasher, read here and written by the round.** `contentIdOf(texts: string[]): string` in `tools/manual/src/store/content-id.mts`, store-side because `node:crypto` has no synchronous browser answer: each text with its whitespace collapsed and trimmed and nothing else touched, joined by a NUL, the first 8 hexadecimal characters of the SHA-256. `reviewed:` maps a schema artifact id to that id over what is before the artifact - the linked page sections first, then each artifact file the schema's `upstream` names. The round change imports the same function to write the line, and one fixture asserts the reader and the writer agree. Rejected: normalising the way `stale.mjs` does, which also strips link targets and scenario ids and would hash two different upstreams alike; a commit sha, which a shallow checkout cannot resolve and a rebase invalidates; a date, which cannot tell two edits on one day apart.
- **The verdict is derived; the reading it compares is the store's.** Two halves, because hashing and the page texts are the store's and the comparison is nobody's: `upstreamOf` in `store/upstream.mts` writes `upstream` onto the entry - the content id of what is before each written artifact, the items in reading order (the linked sections by `<page>#<slug>`, then the schema's `upstream` set), and which of the change's own artifacts a commit dates later than the artifact itself; a commit on a page dates every section of it, so a linked section puts nothing behind until a `reviewed:` line dates the read (Q48) - and `behindOf(entry, artifacts)` in `api/stages.ts` is a pure comparison over it, the recorded `reviewed:` id where the record carries one and the dates otherwise, with no answer at all - so not behind - when either side is undated, which is what a depth-1 checkout gives. `sectionTextOf(page, slug)` in `content/sections.ts` gives a linked section's text: its `## ` heading and the lines under it to the next level-two heading, a callout's and a flow's body inside the section and a `detail` and an `example` left to the page, which is the boundary `questionsOf` counts a section's questions by. `.openspec.yaml` is never upstream and a waived artifact is never behind. No verdict is stored: the artifact row and the card chip call `behindOf`, so a fixture can carry a behind artifact with no repository behind it.
- **`stage` is carried, `behind` is not.** `read-changes.mts` walks the ladder once per change, where the schema is already at hand, and carries `stage` and `heldBy` - the artifact the walk stopped at - on the `ChangeEntry`, because six call sites of `laneOf` would otherwise each have to fetch the schema; `stage` is required on the entry, so `laneOf` is that projection and nothing else. `behindOf` stays a call, because it compares a reading already on the entry and only two surfaces ask.
- **The team map is a store file with one reader.** `docs/prds/team.yaml`: one entry per handle with `email` (the address `git config user.email` gives), `slack` (the member id) and `roles`, and one channel per role. `scripts/openspec/lib/team.mjs` is the only reader: the snapshot imports it so the manual can show a hand's name, the notify script imports it so it can address a message, and the landing resolves a handle from `git config user.email` through it. It needs `yaml`, so the notify job installs the workspace's dependencies. Q40 records its home; the reader takes a path, so moving it is one constant.
- **Idle counts landings, not commits.** `readLandings(root, commit)` in `store/read-landings.mts`, run once from `readChanges` at the revision the task lists are read at: two walks for the whole store, not two per change - `git log -p --unified=0 -M -- 'openspec/changes/*/tasks.md'` for the commits whose net `- [x]` lines and owner tags rose, keyed by the `+++ b/` header, and `git log --name-status -M --diff-filter=A -- openspec/changes` for the commit that added an artifact. `-M` rather than `--no-renames` is the point: a directory rename changes no line and adds no file, so it lands nothing, where `--no-renames` read it as every task of every moved list being ticked at once. The later of the two is `lastLanded`, and `idleDays` is the whole calendar days on the Hong Kong date since it. A change no walk names has none - no repository, a depth-1 checkout - and the chip is not shown rather than read as 0; a walk git will not make is said out loud once and dates nothing. `lastMoved` stays for the board's sort. Rejected: two walks per change, which spawned 144 processes on this store, and excluding a commit by its message or its size, which guesses.
- **Open questions are read from the decisions and the page.** A `## Decisions` row whose `Decided` cell starts with ❓ and names a role, and a ❓ line under a top-level section the proposal links, are the change's open questions: the page half is one walk of `openMarksOfPage` per page, grouped by the section each mark sits under, so a ❓ row inside a `detail` or an `example` stays the page's own. `❓ <role> - <what is recommended>` is the grammar both halves are read by, in `api/stages.ts` beside the hands: the separator is what makes it one, and a page line names its hand by that grammar or by the confirmer it names in prose, the product manager otherwise (Q41). `read-changes.mts` lists the rows with their `Q<n>`, the hand and the recommendation, the change page counts them per artifact, and My turn lists them per hand.
- **The workflow reads the base from one worktree.** `changed-changes.mjs` gains `--stages`: `git worktree add --detach <tmp> <base>` once, the manual's reader run against that root and against the checkout, and `stageOf`, `handOf` and `behindOf` computed on both. The reader reads files from a root, so `git show` cannot serve it, and `changed-changes.mjs` pins its root at module level: `--stages` passes the base root explicitly rather than mutating it. A base commit the checkout cannot resolve fails the step and prints the range it was given: falling back to `HEAD^` would silently narrow a multi-commit push and tell nobody. The worktree is removed in a `finally`.
- **Once per move is the diff; the keys make a re-run idempotent.** A change whose hands changed between base and head sends one direct message to each new hand with the thread link; an artifact newly behind sends one to its hand; the channel post gains the stage after each change. A push whose only change to a record is `reviewed:`, `thread:` or `landed_by:` lines sends no Your turn message, and a push that moved nobody skips the notify step altogether. The script writes the keys it sent - `<change>:<stage>:<role>` and `<change>:behind:<artifact>` - to the file `--sent-keys` names, and the job restores and saves that file under the exact key `notify-sent-<run_id>` with no `restore-keys`: a re-run of one push reads its own keys back, and a stage re-entered after a revert is a different push and sends again. Rejected: a key prefix with `restore-keys`, which drags the previous entry's keys in and silences the re-entry; and `notified:` keys in the record, which makes every message a commit.
- **The notify job is a Node job.** `--stages` imports `read-changes.mts` and the team map's reader, so the job gains `actions/setup-node` at 24.14.1, `pnpm/action-setup` and `pnpm install --frozen-lockfile`, as `lint.yml` does. The workflow's `paths:` gains `docs/prds/**`, because a page landing can put an artifact behind. `vars.SLACK_PLANNING_CHANNEL_ID` names the planning channel, falling back to `vars.SLACK_CHANNEL_ID` the channel post already uses; `vars.NOTIFY_DMS` turns the per-hand messages off - a role's channel among them, which is one hand's message rerouted - without touching the post or the thread's landing reply, which is nobody's inbox. The job keeps `contents: read`, because nothing here commits - `thread:` and `reviewed:` are the round change's writes - so no loop breaker and no actor guard is owed, and the only token it holds is the Slack bot's. A preflight step refuses the run and says which of `SLACK_BOT_TOKEN`, `SLACK_WORKSPACE_URL` and the channel variable is unset.
- **The Slack app's scopes and the thread's link.** The bot needs `chat:write` to post and `im:write` to open a direct message, and it must be a member of each role's channel: the send reports a channel that refused it, naming the channel, after every other message has been tried, and the preflight names only what a run can know before it sends - the unset secret and the missing workspace URL. Rejected: a `conversations.info` probe per channel, which spends a `channels:read` scope on a fact the send already reports. The two CI alerts in `lint.yml` and `storybook.yml` keep `slackapi/slack-github-action`: they address no hand and carry no key, and `scripts/openspec/lib/notify.mjs` is the sender for the planning messages alone. A thread's link is built as `<SLACK_WORKSPACE_URL>/archives/<channel>/p<ts with the dot removed>`, because a permalink needs the workspace host and the timestamp without its separator. Rejected: `chat.getPermalink` per message, which spends a call per hand on a value the record already holds.
- **A run's landing marks its own commit; a person's is bare.** `plan:land` in wake mode, and only there, writes one trailer on the landing commit it cuts - `Wake: <change>@<channel>/<ts>`, the wake as `.round/relay.json` names it - and `--stages` reads the trailers of `<base>..<head>` in one `git log`, `%(trailers:key=Wake,valueonly)` beside `--name-only`: a change whose record a marked commit wrote has had its thread told by the run itself, and every other landing is a person's, told here. The wake's token is never written; it is the run's one credential, and the wake's own number rides inside it signed. The standing "Rejected: a commit trailer" above is about `landed_by:`, the record's own key that every reader parses, not about this marker, which nothing but this one read parses. Rejected: the committer's e-mail resolved through the team map, which names the machine a push came from - a rebase, a second account and a workflow's own identity each answer differently, and a person the map does not hold reads as a run; and a git call whose failure is swallowed, which turns a whole push's landings into a person's without saying so.
- **The thread link is read from the record.** `thread:` names the change's Slack thread; this change reads it into every message and falls back to the change page's link when it is absent. The round change writes it.
- **The staging message names the run sheet.** The message to the QA hand links the run spreadsheet `scripts/openspec/run-sheet.mjs` writes into, because no per-change run tab exists in the store to link (decisions Q39). A tab per change, if the run sheet ever writes one, is a link the same message can carry without a second kind.
- **Unnamed hand routes to a channel.** The team map carries `channels:` per role; a stage whose hand is unnamed posts to that role's channel with the same body, and the card on the board says the hand is open.
- **The digest is a scheduled workflow.** `digest.yml` on `cron: "0 1 * * 1"` - Monday 09:00 on the Hong Kong clock - reading the snapshot's open questions, `idleDays`, the behind set, `awaiting` and `hands`, one direct message per person with at least one line to say; a behind artifact appears after 7 days. `vars.DIGEST_ENABLED` gates it, so the schedule can be stopped without a revert. Rejected: a daily digest, which the page's Messages table rules out.
- **`pnpm plan hand` reuses the claim path.** In `grade10`'s `scripts/openspec/plan.mjs`, `hand` edits the change's `.openspec.yaml` on the store's `main` and pushes one commit, as `claim` does for `tasks.md`. It validates nothing: the store's `hands` rule refuses an unknown role or handle on the push, and duplicating the team map in a zero-dependency script would give two answers. The board there links the change's page rather than printing the stage (decisions Q37).
- **Assign on the local manual writes through the dev server.** The Vite plugin's confined endpoint gains `hands(change, role, handle)`, one atomic commit like `propose`, behind the same path allowlist.
- **The walk is a browser project over the fixture snapshot.** A vitest browser project on `@vitest/browser-playwright`'s chromium, one file per journey under `tools/manual/walk/`, mounting the manual against `public/fixture-snapshot.json` that `pnpm fixture` builds from `tools/manual/demo-store`, and a `walk` job in `test.yml` on pushes to `main` and on pull requests. It decides the cases a reader can see: the board, My turn, the change page and a page's marked line. What it cannot reach - a direct message, the digest, a date read from git history - stays a manual case, and the walk's commit says so.

## Service Interfaces

Not a service. The contracts that cross a boundary:

| Contract | Input | Output |
| --- | --- | --- |
| `stageOf(entry, artifacts)` | A `ChangeEntry` and the schema's artifacts | One stage id; never throws, an unreadable entry is `proposed` with `error` set |
| `ladderOf(entry, artifacts)` | The same | That stage, with `heldBy` - the artifact the walk stopped at, where an artifact is what stopped it |
| `handOf(entry, stage, artifacts)` | A `ChangeEntry`, its stage and the schema's artifacts | The roles whose turn it is, read through the ladder's own settled predicate; `pm` on an unreadable entry |
| `handOfArtifact(id, artifacts)` | An artifact id and the schema's artifacts | The role the schema names as its hand, or nothing |
| `upstreamOf(root, entry, artifacts, pages, asts, git)` | The store root, a `ChangeEntry`, the schema's artifacts, the manual's pages with their parses, and the git index | What is before each written artifact: the content id, the items in reading order, the items a commit dates later than the artifact, the first of those to move and the newest commit among everything before it - written onto the entry as `upstream` |
| `behindOf(entry, artifacts)` | A `ChangeEntry` carrying that reading, and the schema's artifacts | The artifact ids behind, in the schema's order, each with what it is read again against - the items the dates single out, or the whole of what is before it where the recorded id is what says it moved - and the day it went behind: the first thing that moved after the artifact was drawn, or the newest commit before it where a recorded id is what says so, an id dating nothing of its own; an undated artifact is not behind |
| `contentIdOf(texts)` | The upstream texts in the schema's order | 8 hexadecimal characters: the SHA-256 of the texts, each with its whitespace collapsed and trimmed, joined by a NUL |
| `readLandings(root, commit)` | The store root and the revision the task lists are read at | Every change's last commit that ticked a task, claimed a group or added an artifact, as `Map<changeId, isoDate>`; a change no history dates is not in it |
| `changed-changes.mjs --stages` | `--base`, `--head`, `--sent-keys <file>`, the team map path | The channel payload with a stage per change, one direct-message payload per hand change keyed `<change>:<stage>:<role>`, one per artifact newly behind keyed `<change>:behind:<artifact>`, and the keys it sent appended to the file |

The team map:

```yaml
handles:
  ecchochan: { email: ecchochan@gmail.com, slack: U0123ABCD, roles: [pm, dev] }
channels:
  design: C0456EFGH
```

## Risks / Trade-offs

- [The workflow sends to a wrong person after a rename] → the `hands` and `landed_by` rules refuse a handle the map does not hold, on the push that renamed it, before any message goes out
- [A rebase replays a stage entry and a second message goes out] → the `<change>:<stage>:<role>` key in the workflow cache; a duplicate is dropped
- [A stage flips back and forth on a half-written change] → the message says the stage and the file that proved it; a flip back sends nothing, only a rise does
- [Idle reads wrong on a change planned by hand edits] → a hand edit to `tasks.md` still changes a line the reader counts as a landing
- [A reformat of a proposal puts every artifact after it behind] → the chip is honest, and the round change's re-read clears it with one record line per artifact
- [Eight lanes make a long page] → a lane collapses to its heading unless its stage names a hand, a lane with nothing in it always collapses, and the lanes stack down the reading column as In Flight's four stack today

## Migration Plan

1. `stageOf`, `handOf`, `upstreamOf` and `behindOf`, the eight lanes with the agent mark and the move, the stepper and the pip; `landed_by:` and `reviewed:` read; no message yet. Nothing changes for anybody who writes a change.
2. `hands:`, the team map, the `hands` and `landed_by` rules, `pnpm plan hand`, Assign on the local manual, My turn. Changes without hands show open hands.
3. `--stages` in the workflow, the direct messages, then the digest. Rollback for this step is `vars.NOTIFY_DMS` and `vars.DIGEST_ENABLED`; steps 1 and 2 need none.
4. The walk of the surfaces the first two steps built, and the suite's automated cases flipped in the same commit.
