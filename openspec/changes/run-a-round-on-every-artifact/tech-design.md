Drawn from [Agent Rounds](../../docs/prds/products/shared/planning/agent-rounds.md), the proposal and the journeys, before the requirements. The requirements pass reads it; the reconciliation re-reads it.

## Context

- **The skills already run rounds by hand.** `planning-pm` interviews through `grilling`, `planning-qa` dispatches two blind sub-agents and reconciles, `planning-design` and `planning-dev` write one file each; every rule an artifact must meet is rendered by `openspec instructions <artifact>` from `schema.yaml` and `openspec/config.yaml`, which is the load path a round reads.
- **Freshness is read from text because history is not always there.** `tools/manual/check/stale.mjs` compares a spec's requirements as they stood at the page's commit with whitespace collapsed. `tools/manual/src/store/git.mts` does walk full history — it is how `lastLanded` is read — but a depth-1 checkout, which is what CI takes by default, dates nothing: every commit reads as the same one. That is why no check reads freshness from a date, and why the content id is a hash of the text a one-commit checkout can still read.
- **`stage-changes-and-notify-hands` derives everything this change acts on.** `stageOf`, `handOf` and `behindOf` in `derive.ts`; `reviewed:`, `landed_by:` and `thread:` read by `read-changes.mts`; the push workflow computing the stage, the hands and the behind set at base and head, on a full checkout, with the Slack bot token.
- **Two repositories, one submodule.** Code lands in `grade10`, which carries this store as `external/grade10-spec`; `pnpm plan done` there pushes the tick to this store's `main`.
- **What a thread can hold.** A Slack app can post replies in a thread it can see; a second app cannot answer inside another app's direct message, so a thread every hand and every agent can use sits in a channel.
- **The hosted runner's push check.** A Claude Code Routine's session pushes freely to branches prefixed `claude/`; a push to any other branch is refused when the branch is protected, when somebody else has an open pull request from it, or when it carries a commit authored by somebody other than the routine's owner. Every firing is a fresh session, and the payload an API trigger carries arrives labelled as data.

## Goals / Non-Goals

**Goals:**

- One round procedure, one set of perspectives per artifact, read by every line skill from the load path
- A re-read that clears Behind with a record no person has to write, and a landing that refuses while anything before it is behind
- A thread a person can work a change from, and a wake on every landing; a run keeps no state between wakes but the files and the thread
- One relay per store that wakes a run, lets it post, and moves `main` on a human word it checked itself

**Non-Goals:**

- A runner of our own: the session is the vendor's hosted Routine, and the relay is glue between Slack, the Routine and the code host that holds no model
- `pnpm land` as the one gate for both repositories - the round's landing step runs the same checks until that change lands
- A Slack surface beyond the one Confirm button a summary carries (`Q90`)

## Decisions

The page governs what a round is and what a hand can say; these are how that lands.

- **The round is one skill.** `.claude/skills/workflow-round/SKILL.md` holds the six steps: read what is before the artifact, draft on `claude/<id>`, dispatch one challenger per perspective, dispatch one verifier per group of findings, write the summary and the questions to the thread, land on the hand's word. `/workflow-plan`, `/workflow-design`, `/workflow-tech`, `/workflow-specify`, `/workflow-tasks`, `/workflow-build` and `/workflow-land` each name their artifact and call it, standing beside the planning skills until `land-on-main-through-the-gate` consolidates them; `/workflow-specify` sets its Challenge to the two blind readings and its Verify to the reconciliation and keeps the scenario draft out of the branch. Rejected: the procedure repeated in each skill, which `agent:check-parity` cannot hold together.
- **Perspectives are schema data, read by our own reader.** `perspectives:` beside `teammate:` on each artifact in `openspec/schemas/grade10-planning/schema.yaml`, one entry per reader with `name`, `when` (what in the draft summons it: `surface`, `schema`, `export`, `system`, `migration`, `flag`, `money`, `deploy`, `copy`, `always`) and the prompt file under `.claude/agents/`. A task group is no artifact of the schema, so its readers sit as `perspectives:` on the schema's `apply:` block. `tools/manual/src/store/read-schema.mts` gains the key and `apply.perspectives` beside it, and the round, the surfaces and the checks all read it from there. Rejected: a copy of the table in each artifact's `rules` block in `openspec/config.yaml` — the CLI renders those blocks into the instruction budget, forty words at a time, and a table of readers would eat it while leaving two places to keep in step. The simpler-thing reader is `always`.
- **Challengers and verifiers are agent definitions.** One file per perspective under `.claude/agents/`, and one `verifier` definition that takes a group of findings and the draft; the round dispatches them as sub-agents that see the draft and what is before it, and never each other's output. The tech design's and the build's readers cite `docs/governance/system-design.md`.
- **The size is computed from the diff.** The round classifies the diff of the artifact's own files since it was last drawn - never a file's name - against the `when` set: a `## Screens` or `## States` section, a `::story` or `::figma` line is `surface`; a `## Data model` section is `schema`; a `## Service Interfaces` section or an export key term is `export`; a migration group is `migration`, `flag:` is `flag`, minor units are `money`, a prose line is `copy` - and dispatches the readers summoned plus `always`; one reader means no verifier and the writer reconciles. Nothing is declared; a wrong set is a question for the interview.
- **Questions are decisions rows.** A finding the verifier calls a preference or a product decision is written as a `## Decisions` row `Q<n>` with `❓ <role> - recommended: <option>` in `Decided` and the options in `Instead of`; the id is the next unused in the change. A product detail goes to the page as a ❓ line. The thread's message lists the ids; a reply `Q<n>: <answer>` writes the answer into `Decided`, and `Q<n>` alone takes the recommendation. `cited` resolves scenario and journey ids only, so the `round` rule reads the `Q<n>` pattern itself. Two classes of row (`Q59`): a row is held, and keeps the ❓, when it moves scope, is costly to undo, needs a fact only a person has, or divides its options by more than a task group of work; every other preference the round decides on the best option and writes as `<option> - decided by the round`, with what it passed over in Instead of. `plan:land` refuses a landing while a held row is open, naming the rows, and `--with-recommendations` writes each held row's recommendation in the landing commit (`lib/held.mjs` parses the table). My turn and the digest count ❓ rows, so a decided row drops out of them on its own.
- **The read record is a content id, and one function computes it.** `reviewed: <artifact>: <id>` where `id` is the first 8 hex characters of SHA-256 over the artifact's `upstream:` texts in the schema's order, each with its whitespace collapsed and trimmed and nothing else normalised, joined by a NUL. `contentIdOf` lands in the store with `stage-changes-and-notify-hands`, where `behindOf` compares it to the tree; every script here imports it rather than hashing again, so a surface and a landing step can never disagree about what is fresh. A re-read that changes nothing writes the line in one commit that says so in the thread; a re-read that edits opens a round and writes nothing. `.openspec.yaml` is excluded from every upstream set.
- **The relay wakes the run, and every run is a fresh session.** `tools/relay` is a Cloudflare Worker with one Durable Object per change (`Q52`, `Q61`); its endpoints, its room and its checks are tabled under Service Interfaces. It verifies the Slack app's events, drops a repeat of one message (keyed by the message's channel and ts, since one mention arrives twice) and a bot's post, debounces a burst of replies for a minute, carries the messages the events delivered since the previous wake (`Q82`), fires the Routine's API trigger with a data payload (`Q63`), and posts the acknowledgment with the run's link. The push workflow's `reread` job posts one `/wake` per change a landing put behind, with the change and the head, and nothing else: no session and no write permission in the workflow, and the bot token in its plain steps alone, never in a session (`Q62`). Its bounds:

  | Bound | Why |
  | --- | --- |
  | One room per change; the opening message's thread room forwards to it once the run names the change, and a landing wake finds the thread in the record's `thread:` at `main` | Two rooms for one change are two runs on one branch |
  | One running wake per room; a message during a run sets the room dirty and fires again after `done`, carrying every message since the previous wake | A run that starts after the last reply reads it |
  | A minute's debounce on a reply, none on a plan or a landing | Three quick replies are one wake; the dirty flag re-fires rather than collapses, so the minute is what makes a burst one reading |
  | The wake token: HMAC over the room, the wake and its expiry, carried in the run endpoints' path, valid for the wake's budget | A post or a landing carries proof of the wake it belongs to, the bot token never leaves the relay, and a run whose wake was closed under it is refused and stops pushing |
  | Budgets by the wake's reason: thirty minutes on a reply or a landing, two hours on a plan (`Q57`, `Q64`); the run pushes after every artifact | A run that dies loses one artifact; a hung run frees the thread |
  | The alarm is armed when the wake is queued; a fire the runner refuses, and a run that never says `done`, post the failure line with the run's link when there is one (`Q56`) | The runner offers no completion webhook, and a run that dies silently looks like a run that found nothing |
  | The room keeps the last landing word until a landing consumes it | A chain the budget cuts halfway is finished by the next wake on the same word |
  | The relay moves `main` only as a fast-forward, only after its own checks (`Q54`, `Q55`); the run checks the exact writable set itself with `reread-guard.mjs` before every push of an artifact's draft, a task group's code being what its tasks name, and the relay's path check is the coarse superset | The hosted runner refuses a push to `main`, and a word the run reports is not a word the relay saw |
  | `/wake` is keyed by the change and the head; the matrix excludes a push whose only change is `reviewed:`, `thread:` or `landed_by:` lines | A repeated push is one wake, and the re-read's own commit does not wake another re-read, which is what makes the loop terminate |
  | The whole `reread` job behind `AGENT_REREAD`, off until the relay is deployed | Operations turns the cascade on |

  The room is a cache of what the thread and the record already hold - the lock, the messages the events delivered since the previous wake, the deliveries it has answered, the last landing word and the two timers - and a lost room drops at most one debounce, one alarm and the messages of one burst, which the next message or wake rebuilds (`Q82`); a stateless Worker cannot hold the lock, the debounce or the alarm, which is what the Durable Object pays for. Rejected: the vendor's action running the session inside the workflow, which needed `contents: write`, a settings file and a guard step in the job and still could not hold a thread; a completion webhook, which the runner does not offer; Claude Tag, whose pairing and spend nobody could confirm.
- **The thread is in the record, and the room reads it.** `pnpm run round:thread <change> <channel>/<ts>` writes `thread:` once, called by the round when it answers the first planning-channel message about a change - the sentence that opened it, or the first later message naming it - and the run tells the relay the change's id with `relay-post.mjs --bind <change>`, which makes the thread the change room's alias for the rest of the conversation and never defines the record: the record's `thread:` at `main` is the key a landing wake resolves, and a change whose record names no thread is answered in the planning channel. The push workflow never writes `thread:`: its own per-push post is a channel message about several changes, not any change's thread. A run posts through the relay with its wake token and never holds the bot token; a terminal run posts nothing, and the push tells the thread. What Operations sets up is `docs/references/agent-runner.md`. Rejected: the room as the only holder of the mapping, which a terminal-opened change or a redeployed room would leave without a thread.
- **Resumable, not idempotent.** Every run starts by reading the branch, `main` and the wake's file, whose messages are the thread's words since the previous wake, computing what is behind and which questions are open, and continues from there; a session that dies loses nothing that was pushed, and every wake is a fresh session that remembers nothing else. Every push to the branch is `--force-with-lease`; `main` moves as a fast-forward, by the terminal's own push or by the relay; a loser re-reads once and, if it loses again, replies in the thread and stops; a run whose wake token the relay refuses stops and pushes nothing further.
- **A wake drafts the chain and one word lands it.** A wake that opens a change or is asked to plan drafts every artifact it can reach on `claude/<id>` - the proposal, the decisions, the journeys, the design where a surface moves, the tech design, the requirements and the cases, the plan - each from the draft before it and each with its own readers, pushing after every artifact and landing nothing (`Q58`); a re-read that edits does the same from the artifact it reached, and every redrawn artifact opens a round for its hand. A draft that needs what only a hand holds writes the dated wait and drafts nothing that depends on it. The readers of one round are computed from the diff of that artifact's own files against what it was last drawn from, never the branch's whole diff, so the design's `surface` does not summon readers onto the plan. `land` lands every drafted artifact of the speaker's hand in order and stops at the first artifact of another hand, who is told; while a held row is open it lands nothing and names the rows, and `land with recommendations` takes them (`Q60`): that is an answer, so the landing commit that writes the recommendations also writes a `reviewed:` line for every drafted artifact after the decisions, which the run drew from those recommendations, and nothing goes behind. Rejected: stopping at the first hand, which puts a plan of seven artifacts behind seven replies; a fast-forward of the branch tip, which carries every unlanded draft onto `main`.
- **The landing step is one transaction.** `pnpm run plan:land <change> <artifact|group>` in this store, in this order, stopping at the first refusal:

  1. Refuse a dirty working tree or a rebase in progress - a landing that carries somebody's uncommitted edit is not a landing
  2. Resolve the hand once: with `.round/relay.json` naming a wake, the wake's sender, and a wake with no sender lands only `--reviewed`; otherwise `git config user.email` through the team map, refusing an e-mail the map does not name and a handle that is not the hand of the stage, naming whose word it waits on; `--as @handle` is taken only where it resolves to the same e-mail
  3. `git fetch origin main`, record that sha as `MAIN`, and rebase the change's branch on it
  4. Refuse when `behindOf` names anything before the artifact, and name it and its hand; refuse while a `❓` row is open, naming the rows, unless `--with-recommendations` takes them; the rows are read through the manual's own question reader, never a second parser; bound to a wake, ask `GET /runs/<token>/alive` once and stop on anything but 200 (`Q81`)
  5. Cut the landing commit `L` from `MAIN`: for an artifact, its own files (the schema's `generates:` glob), the change's `.openspec.yaml` with `landed_by:`, `rounds.md` with the round's row, `decisions.md` wherever this landing carries it - the flag's rewrite of the held rows, or the hand's own answer - with a `reviewed:` line for every artifact drafted after it, and the pages the proposal links, the set `reread-guard.mjs` holds every push of an artifact's draft to; for a task group, the rebased branch tip, since nothing is drafted ahead at Building
  6. Run the gate - `validate:changes`, `check:manual`, `tcs:validate` - against `L`'s tree with `PLAN_NO_FETCH=1`; a refusal leaves the branch and the working tree as they were, `L` never having touched them
  7. `main`: a plain fast-forward `push L:main` from a terminal, or, bound to a wake, `L` pushed to the side ref `claude/<change>-landing` - never over the branch - then `POST /runs/<token>/land` with `L`'s sha, the kind and the artifact, the relay moving `main` after its checks and the side ref deleted once it has answered
  8. Rebase the branch onto `L`, so the drafts sit above the landing, and `git push --force-with-lease=refs/heads/<branch>:<the sha the run read>`
  9. On a 409 from the relay, or a push the remote rejected because the ref moved under it, re-read `main` once and retry from 3; losing again, reply in the thread and stop. Every other status the relay gives - a 403 names the check it failed - and every other way git can refuse a push stops the run, naming the status and the relay's reason or git's own stderr

  `pnpm land` becomes this step when `land-on-main-through-the-gate` makes one gate for both repositories (`Q36`). The fold's refusal on a behind delta is `stage-changes-and-notify-hands`' (`Q37`).
- **`rounds.md` is a table.** `| Round | Artifact | Perspectives | Stood | Asked | Tests |`: the round number, the artifact id or the task group number, the perspective names run, the findings that stood as short phrases, the `Q<n>` ids raised, and per scenario id the test files that landed for a group. `read-change-documents.mts` reads it; `check:manual` gains rule `round`: a written artifact from `proposal` to `tasks` and a ticked group with no row is refused on a change on the round - a `landed_by:` line, or a row - whatever its date, and on every change created from `ROUND_RECORD_SINCE`, the day after the kept skills go, unset until then and set at this change's archive (Q96, Q97). The archive copies the file across like the journeys.
- **One module holds the words, and the change page mirrors them.** `scripts/openspec/lib/wording.mjs` composes every sentence a hand is sent - `yourTurnText`, `stagingText`, `behindText`, `landedText`, the `toldBodyOf` rule that picks which of the first two a hand of a stage gets, `threadPathOf` and `linkedOf` - with no `node:` import of its own, so the push workflow and the manual's Told now read one text and no module re-exports a sentence. `TCS_SHEET_URL` reaches the browser in the snapshot, the way `RELAY_URL` reaches it in `/api/relay`, so the sheet QA is sent to is the same link in both. The states the code chose, which `ui-design.md` does not carry because it is the designer's input the build was read against: Told now draws one quoted block per hand of the stage and one for the earliest behind artifact, the handle or the role's channel above each, and says so in one line where the stage waits on no hand; the Thread draws one row per commit of the change's directory on `main`, oldest first, with the round that commit recorded as a second line under its landing, a round no landing accounts for as a row of its own in round order, every held `decisions.md` row dated by the commit that asked it, and a line saying so where the reading has no commits.
- **A remark is carried to the landing.** A reply that is not `Q<n>` and not a landing word is a remark: the round applies it as written, re-runs the perspectives whose `when` the edited lines summon, carries the remark into the landing's row as what stood - the landing writes every row, in its own commit - and, when the remark settles a choice a decisions row asked, writes it there too.
- **The first sentence opens the change.** A message in the planning channel mentioning the app with no change named runs `/workflow-plan` from nothing: `slugOf` from `tools/manual/src/editor/propose.ts` picks the id, `openspec new change` writes the record, `hands: pm:` is the asker's handle from the team map, the branch is pushed, and the reply names the id in the thread the message started, which `round:thread` records.
- **The tech design moves before the requirements, in the other change.** Moving `tech-design` above `specs` in the artifact list and setting its `requires` to `decisions` and `user-journeys` is `stage-changes-and-notify-hands`' task: it opens `schema.yaml` for the stage's derivation, and two changes editing one list in one week is a conflict for nothing. This change adds `perspectives:` and `upstream:` to the same file afterwards. What is ours: `planning-qa`'s requirements pass reads `tech-design.md` beside `ui-design.md`, and a requirement that reaches the design writes `awaiting: tech-design: "<date>, <requirement> re-read - @<tech>"`, cleared by the tech PIC's edit or a `reviewed:` line.
- **The build round runs in the application repository, reading the rules from here.** `grade10` carries its own thin `/workflow-build` and `/workflow-round` skills that name this store's rules and hold no copy of them: a session there runs `/add-dir` on a clone of this store and reads the `workflow-round` skill, the schema's `perspectives:` and the reader prompts under `.claude/agents/` from that clone. Never from `external/grade10-spec`, the submodule pinned to an older sha - a round read from a pin is a round held to last month's rules. `/workflow-build` runs the six steps against a task group: the tests the group's scenario ids name in their own commit first, then the code, then the group's readers from `apply.perspectives`, then the landing summary in the thread. `pnpm plan done` refuses a tick naming a scenario id no test in the tree its group's repository tag names cites, and accepts a task that names none; the round row lands in the store before the tick.
- **Flipping a case's automation status is a file edit.** `pnpm run tcs:automated <case…> --decided-by <path…>` here edits the `**Automation status:**` line and writes the `**Decided by:**` line in one place, refusing a flip that names no test (`Q74`), and pushes nothing - the walk's own commit carries it, which is what makes the flip and the suite one landing. In `grade10`, `pnpm plan automated` does the same over this store's checkout, as `pnpm plan done` does for a tick. `scripts/openspec/run-sheet.mjs` gains `--include-automated`, off by default. The suite runs on every push to `main`; its `smoke` cases on a staging deploy and a release cut belong to the release line's change (`Q35`).
- **The principles are a rulebook.** `docs/governance/system-design.md`: eight principles with one test each, and the reader's stance; `AGENTS.md` maps to it; the `tech` and `build` readers cite it.

## Service Interfaces

The relay is the one service this change ships; the store's own contracts follow it.

### The relay

| Endpoint | In | Out |
| --- | --- | --- |
| `POST /slack/events` | The Slack app's `message.channels` events, signed | 200 within three seconds; the work runs after the answer, and a room that fails posts the failure line |
| `POST /slack/actions` | A Confirm button pressed, signed: the interaction as a form whose one `payload` field holds the JSON | 200 with an empty body within three seconds; the word queues as the reply the press stands for, the thread reads who pressed, and the button is replaced by who confirmed it. A signed body with no press in it - Slack's own `ssl_check` when the request URL is saved - is answered, not refused |
| `POST /wake`, bearer `WAKE_TOKEN` | `{ change, reason: "landing", head }`; the head keys the wake | The room's own answer: `{ queued: true }`, or `{ queued: false, why: "duplicate" }` on a head it has already taken; 400 with no `change` or `head` |
| `POST /runs/<token>/bind`, the wake token in the path | `{ change }` | The change's room takes the thread as its alias and what the thread's room had queued; the wake stays where it started; 409 while the change's room runs a wake of its own, which the run asks again |
| `POST /runs/<token>/post` | `{ text, confirm }`, where `confirm` is `{ label, word }` and the run names both | A reply in the thread, or in the planning channel where the record names no thread; `confirm` draws it with one button under it |
| `POST /runs/<token>/land` | `{ sha, kind: "word" \| "reviewed", artifact }` | `main` moved to `sha`; 400 on a sha that is not one, no artifact or no change bound; 403 naming the check that refused; 409 when `main` moved; 503 with the host's own message when the host did not answer |
| `POST /runs/<token>/done` | `{}` | The wake closed; the room fires again when dirty |
| `GET /runs/<token>/alive`, the wake token in the path | - | 200 while the wake is the room's current one, else 401 |

The room is a pure step `(state, event, now) -> (state, effects)` in `tools/relay/src/room-state.ts`, carried out by the Durable Object; its states are idle and running, with a bounded list of the deliveries it has seen, a bounded list of what queued since the previous wake, the last landing word - kept until a landing consumes it - and two timers. The checks before `main` moves (`Q55`): on a word, the Slack member who said a landing word - the latest such message of the wake, a leading mention stripped - resolves through the team map at `main` - a landing sha cannot add its own sender, and `Q55` attaches the sha to the record, not the map - to the artifact's `hand:` in the record at that sha (a task group takes the `tasks` artifact's hand; an artifact the schema does not name is refused), for an artifact the record's `landed_by:` at the sha equals that handle, and every path of the compare falls under the change's directory, `docs/prds/` or `docs/references/` - the coarse superset of the writable set, which the run's guard holds exactly before it pushes - while a task group's landing runs no path check at the relay (`Q68`); on a reviewed landing, the record at the sha and at `main` differ under `reviewed:` alone, read as YAML; a compare the host truncates is refused. Its secrets are `SLACK_SIGNING_SECRET`, `SLACK_BOT_TOKEN`, `ROUTINE_FIRE_URL`, `ROUTINE_TOKEN`, `GITHUB_TOKEN`, `TOKEN_SECRET` and `WAKE_TOKEN`, refused blank at the router's entry; its variables `PLANNING_CHANNEL`, `REPO`, `RELAY_URL` and `SLACK_APP_USER`, the app's own member id; the Routine's fixed prompt is `tools/relay/routine-prompt.md`.

The payload the Routine receives, as data (`Q63`):

```json
{
  "relay": { "url": "https://…", "token": "…" },
  "change": "<id or null>",
  "reason": "plan | message | landing",
  "thread": { "channel": "C…", "ts": "…" },
  "sender": { "slack": "U…", "handle": "ecchochan" },
  "messages": [{ "handle": "ecchochan", "slack": "U…", "text": "…", "ts": "…" }]
}
```

The run writes it whole to `.round/relay.json`, which `lib/relay.mjs` - the one client `relay-post.mjs` and `plan-land.mjs` share - reads for the url, the token, the change, the sender and the thread; with `ROUND_WAKE=relay` in the environment and no such file, a post fails rather than prints.

## Risks / Trade-offs

- [A wrong no-op re-read leaves a stale artifact looking fresh] → the line is landed by the agent alone and says in the thread what it read; the hand of the artifact is told once, and a remark reopens the round
- [A reformat of one upstream file puts every artifact after it behind] → one re-read writes one line per artifact and lands them in one reviewed-only commit cut from `main`; the cost is one run
- [Two runs race on one branch] → one running wake per change in the relay, a wake token that outlives no budget, force-with-lease everywhere, a loser stops and says so
- [The relay is down, or the Routine refuses a firing] → the terminal runs the same round against the same branch; the workflow's wake fails loudly and the push's own messages still went out; a burst of replies waits in the room rather than being dropped
- [A payload talks the run into landing] → the relay checks the word itself, against the Slack event it holds and the record at the sha, before `main` moves; the run's claim is not enough
