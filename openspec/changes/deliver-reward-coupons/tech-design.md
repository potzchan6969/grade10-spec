## Context

`packages/loyalty/backend/src/services/rewards` issues a coupon with today's flat-amount default; `packages/grade10-store/backend/src/services/coupons` prices and applies whatever definition a coupon carries. This change gives the reward its real definition shape and unifies physical-reward settlement onto the coupon mechanism — but two of its decisions turn on state owned by `mint-coupons-as-discount-codes`, a sibling change also under review, so they are pinned here rather than left to an implementer's inference.

## Decisions

**A reward's coupon lives in loyalty's own tables, never `grade10-store`'s `coupons` table — so retiring the till's collection-confirm step (task 3.2) depends on `mint-coupons-as-discount-codes` task 3.7 specifically, not on that change's group 1.** `packages/loyalty/backend/src/services/rewards/coupons.ts`'s `couponInstances`/`couponUsages` are entirely separate from `packages/grade10-store/backend/src/db/schema/coupons.ts`'s `coupons` table; a reward is redeemed and held inside loyalty alone, reached from the store only through `orders/promise.ts`'s `reserveRewardCoupon()` calling the `CouponTender` port. `mint-coupons-as-discount-codes`' group 1 (`createCoupon()`'s minting branch) never touches that path at all — it only covers `product`/`gift` kinds in the store's own `coupons` table. The mechanism this change's task 3.2 actually depends on is that change's task 3.7: `reserveRewardCoupon()` itself mints a real, customer-scoped, `usageLimit: 1` Shopify Discount code for the reward's coupon, the moment an order claims it, keyed by `(orderId, args.couponId)` in the `coupon_mints` table that same change introduces. Only once that ships does Shopify itself refuse a second redemption of the code — the same way today's QR/short-code presentation is consumed once. Task 3.1 (settling a physical reward as a 100%-off coupon on its own variant) can land independently; task 3.2 (removing the till's collection-confirm guard) waits on 3.7, not on group 1.

**The staff-assisted notification (task 6.3) fires on settlement, not on Apply.** `discounts.md` states plainly that "nothing is held" until an order is paid, and that Apply is an explicitly re-plannable claim ("a claim, bounded later by what the shop takes") that the store later "trims... to what landed." A notification that fires at Apply can tell a member a benefit was used and then have it trimmed or the whole sale abandoned, with nothing correcting the record — the opposite of "the member's phone is the monitor." The trigger is the paid order (online) or the till's trim-to-landed pass (POS, `discounts.md` step 9), which already tells the member what landed; a benefit whose trim-to-landed pass reported it and whose sale is then abandoned unpaid sends a correction notice, since step 9's own report is what needs correcting — a sale that never reaches step 9 sends nothing, since nothing was ever reported to correct. `specs/grade10-site/store/membership/spec.md`'s requirement and its `SC-75` scenario are rewritten to name this trigger explicitly (see that file) — they previously said "immediately"/"at once," which this decision supersedes; the spec text was stale against this document, not the other way around.

## Risks / Trade-offs

- **The physical-reward collection guard is fully closed once 3.2 ships, not merely narrowed** → `mint-coupons-as-discount-codes` task 3.7's mint is order-keyed through `coupon_mints`, which carries a `(orderId, couponId)` uniqueness constraint (that change's tech-design.md, Decisions) — this closes the concurrent-double-reservation race at the database level, not just at the Shopify-refusal level, because loyalty's own `useCoupon()` already only lets one reservation go from `available` to `reserved` per coupon (`couponInstances.status`, guarded by its own conditional update) before any mint is attempted. Two near-simultaneous redemption attempts therefore never both reach the mint step for the same coupon; whichever wins the reservation is the only one that can mint. No residual window is accepted here — if this change's own verification (task 3.3) or `mint-coupons-as-discount-codes`' staging verification finds one, treat it as a bug in this decision, not a known trade-off.
- **A reward's coupon minting a real code means `orders/eventSink.ts`'s `providerArtifact` construction and `checkoutRequest.ts`'s `discountCodes` both need a reward-specific read** (`mint-coupons-as-discount-codes` tasks 3.6/3.8) — this change's task 3.2 must not land ahead of those, or the till's collection-confirm guard would be removed before the draft order actually carries the reward's code.

## Migration Plan

Additive: a reward's contract gains fields it did not carry before (kind, discount, scope), and a physical reward's redemption changes shape (coupon instead of an item-owed record) only for redemptions issued after this change ships. No backfill of already-issued physical-reward redemptions is in scope; they settle under the collection-confirm path already in place until task 3.2 lands.
