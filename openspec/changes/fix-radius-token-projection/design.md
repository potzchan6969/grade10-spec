# Design: fix radius token projection

Delete seven declarations so the radius utilities read the tokens they are
named after. The interesting part is not the deletion; it is why deleting is
the fix rather than rewriting the rungs to reference the tokens.

## Context

`theme.css` is generated by `scripts/build-css.mjs` as three parts: a banner,
the verbatim contents of the engineer-owned `src/theme.preamble.css`, and a
`:root` block emitted from `tokens.json`. The preamble holds one `@theme
inline` block, which is the curated projection deciding which tokens become
Tailwind utilities. The colour rungs there reference their tokens
(`--color-destructive: var(--destructive)`); the radius rungs instead derive a
scale from a single `--radius` knob:

```css
--radius-lg: var(--radius);
--radius-xl: calc(var(--radius) * 1.4);
--radius-4xl: calc(var(--radius) * 2.6);
```

`@theme inline` substitutes the declared expression into the utility rather
than emitting a `var()` reference to the theme variable. Compiling the
Storybook entry confirms it:

```css
.rounded-xl  { border-radius: calc(var(--radius) * 1.4); }
.rounded-4xl { border-radius: calc(var(--radius) * 2.6); }
.rounded-xs  { border-radius: var(--radius-xs); }
```

`rounded-xs` is the tell. It is the one rung the preamble does not declare, and
it is the one rung that reads its token. Every rung the preamble overrides is
wrong; every rung it leaves alone is right.

`--radius` resolves to 8px under `.theme-grade10` (`themes/grade10.css:69`
aliases it to `--radius-lg`, mapped in `tokens.config.json`), so `rounded-xl`
is 8 × 1.4 = 11.2 against a 12px token, and `rounded-4xl` is 20.8 against 32.

## Goals / Non-Goals

**Goals.** Every named radius rung renders its `tokens.json` value. The named
and arbitrary-property spellings agree. A token change in Figma reaches the
utility through the existing `tokens:pull` → `tokens:build` path with no
hand-edit.

**Non-Goals.** Reconciling `rounded-full`, removing `--radius`, converging the
two call-site spellings, or touching the colour, size, or gap rungs.

## Decisions

### Delete the rungs rather than rewrite them to reference the tokens

The obvious repair — make radius look like colour — does not compile. Colour
works because the two names differ: `--color-destructive` in `@theme inline`
references `--destructive` in `:root`. Radius has no such split. Tailwind's
utility namespace for radius is `--radius-*`, and `cssVar("Radius/radius-xl")`
in `build-css.mjs` also produces `--radius-xl`. Writing `--radius-xl:
var(--radius-xl)` inside `@theme inline` is self-referential.

Escaping that would mean renaming the primitive side — a config rename rule, or
different Figma variable names — which breaks the `rounded-(--radius-*)` call
sites that read the token directly today, and adds a naming indirection nothing
else in the file needs.

Deleting is better because Tailwind's own default registration is already the
shape we want. Its defaults are declared non-inline, so with no override the
utility emits `var(--radius-xl)`. With the rungs gone, the compiled output is:

```css
.rounded-sm  { border-radius: var(--radius-sm); }
.rounded-xl  { border-radius: var(--radius-xl); }
.rounded-4xl { border-radius: var(--radius-4xl); }
```

Which value that `var()` finds is then a plain cascade question, and the
generated `:root` block wins: Tailwind's defaults land in `@layer theme`, while
the token build writes an unlayered `:root`, and unlayered declarations beat
layered ones regardless of import order. Verified in the compiled Storybook
CSS — `--radius-xl: 0.75rem` inside `@layer theme` at line 9, `--radius-xl:
12px` unlayered at line 367.

This is worth stating plainly because it looks like luck and is not: the fix
does not depend on Tailwind's default *values* resembling ours. It depends only
on those defaults being declared non-inline and layered. The values could be
anything.

### The preamble keeps `--radius-pill`

`--radius-pill: 999px` names a value no Tailwind rung claims, so it collides
with nothing and stays. It is also the only radius declaration left in the
preamble, which makes the file's remaining radius surface exactly the thing
`tokens.json` does not cover.

### `--radius` survives with no consumer in this repository

After this change nothing in the radius utilities reads `--radius`. It stays:
it is the shadcn contract slot, `tokens.config.json` maps it to
`Radius/radius-lg`, and a consuming application may bind it. Removing it is a
contract question for a separate change, and one this change does not need to
answer to be correct.

## Risks / Trade-offs

**Every rounded corner in the system moves.** Named rungs are used at 31 sites.
Four rungs change: `sm` 4.8→4 (5 sites), `md` 6.4→6 (13 sites), `xl` 11.2→12
(2 sites), `4xl` 20.8→32 (1 site). `lg` (12 sites) is unchanged, and
`2xl`/`3xl` have no named call sites. The sub-pixel moves on `sm` and `md` are
invisible; the `4xl` move on the store-home hero is 11px and is the whole point
— it is the rung Figma draws at 32.

**Story coverage does not catch this.** All 526 story tests passed both before
and after the change, because none of them assert a border-radius — the drift
was invisible to every check in this repository except `figma:audit`, and that
only sees a rung a block's `audit.json` maps to a node. Passing tests are not
evidence the scale is right; they are evidence nothing tests it.

**The single-knob affordance goes away.** Setting `--radius` no longer rounds
or sharpens the whole system proportionally. Nothing in this repository used it
that way, and it was the mechanism producing the drift, but a consumer relying
on it would lose it. This is the trade the change makes deliberately:
`tokens.json` owns the scale, or a multiplier does, and the spec says
`tokens.json`.

## Migration Plan

One commit in this repository: the preamble edit and the regenerated
`theme.css` together, since the second is a projection of the first. No
application changes; consumers pick it up on the next submodule bump. No
export contract moves, so nothing in a consuming app fails to compile.

## Open Questions

**Should the check be automated?** The new requirement is testable and nothing
tests it. `figma:audit` catches radius drift only where a block has an
`audit.json` mapping a node. A build-time assertion — no `@theme` declaration
may shadow a name the token build emits — would catch the whole class, and the
gap-, size-, and typography rungs are exposed to the same mistake. Not in this
change; worth its own.
