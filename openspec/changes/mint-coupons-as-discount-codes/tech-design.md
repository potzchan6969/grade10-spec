## Context

`packages/grade10-store/backend/src/services/coupons/create.ts` — `createCoupon()` already mints a real Shopify Discount (`deps.discounts.createCodeDiscount`) for an `order`-kind coupon, at redemption time, then compensates (`deactivateCodeDiscount`) if the local insert that follows fails. A `product` or `gift` coupon takes a separate branch today that inserts a plain row with a generated code and mints nothing.

`packages/grade10-store/backend/src/services/coupons/apply.ts` — `resolveCoupons()` is the shared pricing evaluator (web and POS both call it). It already refuses a second `order`-kind code in one request, but a `product` or `gift` coupon can still resolve alongside an `order` coupon today, welding `lineDiscounts` independently of `orderCodes`.

**A coupon's target can name something Shopify cannot express.** `packages/coupons/contracts/src/schemas.ts` carries two target vocabularies, and the second one's comment states the constraint this whole change turns on: `codeTargetSchema` is "what a shop code can express — Shopify scopes a code to all, products or variants, and knows nothing of our facets." A `facets` target names catalogue facets (`CATALOG_FACET_IDS` is `worlds` and `types`; `ip_worlds` is held by metaobjects of type `commercial_ip`), and only `eligibleLines(target, lines)` can resolve one — against a basket. So a coupon scoped to an IP world has no expressible Shopify target until a basket exists.

**A loyalty reward's coupon is a separate thing from a store coupon.** `packages/loyalty/backend/src/services/rewards/coupons.ts`'s `couponInstances`/`couponUsages` never touch `packages/grade10-store/backend/src/db/schema/coupons.ts`'s `coupons` table — a reward is redeemed, held, and settled entirely inside loyalty's own tables, reached from the store only through the `CouponTender` port. `couponUsages.providerArtifact` already carries a `kind: "discount_code" | "draft_order_discount" | "draft_line_discount"` union, but nothing produces `"discount_code"` today: `orders/eventSink.ts`'s `ownedEvent()` always builds `kind: "draft_line_discount"` for a reward coupon, with the comment "a reward coupon is always a weld ... a shop code is the registry's, and never lands here." That comment is the fact this change makes false.

## Goals / Non-Goals

**Goals:**
- Every coupon reaches a sale as a real Shopify Discount code, so the shop prices it and the paid order names it.
- A coupon scoped to a catalogue facet reaches a sale correctly, by minting against the lines that basket actually holds.
- A checkout never carries more than one discount code, however it got there.

**Non-Goals:**
- Changing coupon eligibility, threshold, or redemption rules. What a coupon is worth is unchanged; only how its value reaches the shop changes.
- A new Shopify discount value type — everything mints as `fixed_amount`. `ShopifyDiscountValue` allows only that, deliberately: "a rate is never minted as a code", because the paid order names a code but not what it took.
- Giving `packages/loyalty/backend` a Shopify integration of its own. A reward's coupon mints through the store side; loyalty only ever receives back a `providerArtifact` describing what the store minted.

## Decisions

**A code is ephemeral. One mint timing: a code is minted when an order claims the coupon, never when the coupon is issued.** The coupon is the durable record and lives in Grade10's own database; a Shopify Discount code is an intention to spend that coupon on one basket, and is what binds it to an order. Only a paid order realises it.

This is forced, not chosen. A `product` coupon may carry a `facets` target, `codeTargetSchema` cannot express one, and `eligibleLines()` resolves one only against a basket — so a facet-scoped coupon has no mintable target until an order claims it. Mint timing therefore cannot vary by coupon shape without re-deriving that split at every call site, so it does not vary at all:

| What is minted | When | Target it carries |
| --- | --- | --- |
| Every coupon — `order`, `product`, `gift`, and a reward's own | The moment an order claims it: checkout submit online, Apply at the till | The cut the evaluator just made against that basket |

Consequences, all of them subtractive: `canMintAtRedemption` is not built; there is no mint-timing table for a call site to branch on; `createCoupon()` stops minting and stops writing `coupons.shopify_node_id`; no backfill is needed, because no pre-change coupon's code has to change; and `ck_coupons_shape` needs only a relaxing edit (see Migration Plan) rather than the tightening a redemption-time mint would have forced.

**`codeSays(definition, evaluation, giftPrices)` reads a code's money and target off the cut the evaluator already made.** Not off the definition's own target re-resolved against the basket: a coupon that reached two of three eligible lines must not scope its code to the third, and a `facets` target has no form the shop can express until a basket resolves it. The evaluation's three arms are exclusive, so exactly one answer comes back — a gift gives `{ kind: "variants", variantIds: [the gift] }` at the line's own price, line cuts give the variants they landed on and their total, and an order cut gives the definition's own target, which is already one the shop can express. `null` where a coupon takes nothing, which refuses the mint rather than standing a code worth nothing.

It lives in `mintOrder.ts` beside the one caller, because a cut is what it reads and only the mint holds one.

The amount is settled the same way and at the same moment: every mint carries `value: { kind: "fixed_amount", amountMinor }`, summed from the evaluation's own `orderCutMinor`/`lineCuts` for that basket. A percentage-with-ceiling benefit needs no special case — its ceiling is applied by the evaluator before the mint, which is what `ShopifyDiscountValue`'s fixed-amount-only rule already requires of every caller.

**One generate-code/retry/compensate implementation, shared by every mint call site.** `create.ts`'s existing loop (code generation, retry on `codeTaken` up to `MINT_ATTEMPTS`, repair-then-refuse on `customerRefused`, `compensateMint`/`deactivateCodeDiscount` on a later failure) is extracted into `mintDiscountCode(deps, params) -> outcome`, parametrized by the value, target, scope and lifetime to mint, and kept inside `packages/grade10-store/backend` — every caller already lives in that package.

**Every mint happens after the order row is committed, and keys on that row's own id.** Not inside `reserveRewardCoupon()`, and not on an id the caller invented. `reserveRewardCoupon()` runs at `promise.ts:213`; the order row is not inserted until the transaction at `promise.ts:301`, and three refusal paths sit in between — `priceGifts` (a withdrawn gift variant), `quotePoints` (`noGoods` whenever the basket's points basis is zero, which a basket-covering reward coupon produces on its own, plus `unavailable` on any programme outage), and the insert's own id guard. Each calls `releaseReward` and returns, so a mint placed before them leaves a live, customer-scoped, single-use code that nothing in grade10 can find: there is no order row to hang compensation on, and `adoptUnreportedCodes` filters `coupons.kind = 'order'` and cannot see a reward coupon at all.

So both mints happen at the one seam the checkout already has: after `promiseOrder` returns and before `buildCheckoutRequest`. A mint failure there is answered the way the shop's own `couponRefused` already is — `applyOrderTransition(failed)`, which runs `releaseCouponTender` and puts the coupon back in the member's wallet. At the till, the same rule reads as the session's standing order row: `planTillSale` passes `crypto.randomUUID()` on every Apply while `upsertPromisedOrder` conflicts on `(paymentProvider, paymentCheckoutRef)` and keeps the first plan's id, so a mint keyed on the argument would miss its own prior row on every re-plan and stack up to `TILL_PLAN_CAP` live codes on one sale. The key is the resolved row's id, always.

**`coupon_mints` records a store coupon's mint; a reward's rides the `orders` row it already has columns on.** `coupon_mints` is `{ orderId uuid references orders.id on delete cascade, couponId uuid references coupons.id, nodeId, code, state, unique(orderId, couponId) }` — real foreign keys on both, which is only possible because the mint now follows the commit. A reward's `nodeId` and `code` go on the `orders` row beside the `loyaltyCouponId` / `loyaltyCouponUsageId` / `loyaltyCouponApplication` columns already there, held null-together by the same shape of check as `ck_orders_coupon_reservation`. That deletes the polymorphic non-foreign-keyed `couponId`, the `origin` discriminator that existed only to say which id space a value came from, and the second lookup every read site would otherwise need: the reward's code arrives on the row the caller has already read.

`state` is `live | dead | spent`. A deactivated mint is marked dead, never deleted, because a failed `deactivateCodeDiscount` needs the `nodeId` to retry — the same reason `compensateMint` already keeps a node id and counts `store.coupons.orphan_discount` rather than dropping the record.

**A mint's `endsAt` is the order's own horizon, not the coupon's.** `create.ts` sets `endsAt` from the coupon's validity — right when the code *is* the coupon, wrong for one that is an intention to spend it. Every mint ends at a single store-side constant of 24 hours, commented as matching loyalty's `STALE_RESERVATION_HOURS`, so a code cannot outlive the reservation behind it. This is what makes every missed deactivation self-heal: a code that escapes its order — a `failed` checkout, an `expired` POS promise, a dropped ride, a deactivation the retire loop swallowed — dies within a day instead of staying spendable for up to `MAX_COUPON_VALID_DAYS`. Deactivation stays as the fast path; its failure degrades to "dies a bit later" rather than to a standing liability, so no reaping sweep is built.

**A mint is deactivated where the coupon is given back, and nowhere else.** That is the `canceled` and `failed` arm `releaseCouponTender` already uses, plus `dropRides`, which is the single choke point where a ride is deleted off an order that still lives. Never on `expired`: `retire.ts` expires a superseded POS promise deliberately, because "the cart can still collect, and `paid` is reachable from `expired`", and `transitions.ts` excludes `expired` from the release for the same reason — deactivating there kills the code of a sale the counter is about to charge against, and the member pays full price for a discount Apply already showed them. The `endsAt` above is what bounds the expired case instead, safely: a lifetime fixed at mint time cannot fire mid-sale.

**A re-plan reuses its mint; it never stacks a second code.** The extension can remove all discounts or its own custom cart discount, but not one code — so a re-plan that deactivated the prior mint and minted fresh would leave both codes on the cart, up to `TILL_PLAN_CAP` of them, with only the last one recorded. Where the coupon still rides, the existing `coupon_mints` row is reused. Where its cut has changed, that coupon is refused on that re-plan with the sentence staff already read for a code that will not come off, because a changed amount on an unremovable code is the one case the till cannot express.

**Every minted code is scoped to the redeeming member, unconditionally**, not gated on `onlineCodeScope === "customer"` the way an order coupon's `codeScope()` is today. A real code redeemed at Shopify's hosted checkout field or POS's native discount box bypasses both `resolveCoupons()`'s `not_owner` check and loyalty's ownership-checked `useCoupon()`, so an unscoped mint would be a bearer string. A member with no paired Shopify customer refuses the mint rather than falling back to `{kind: 'all'}` — and that refusal is named and counted, not reported as "your coupon was refused", because a pairing parked in `conflict` is terminal until an operator unparks it. `checkout.ts`'s deliberate retry with `customerRef: null` is skipped when the request carries any code, since it can only refuse.

**A code carries its own coupon's combine setting; grade10 evaluates nothing.** `COMBINES_WITH` (`orderDiscounts: false`, `productDiscounts: true`, `shippingDiscounts: true`) is a module constant baked into every code today, so a merchandiser cannot author an order-threshold automatic that stacks with a member's coupon whatever they set in Shopify Admin. `combinesWith` becomes a parameter of `mintDiscountCode`, sourced from the coupon's definition — a reward's definition carries it (`deliver-reward-coupons` task 1.5), and the operator's mint of a store coupon gains the same three switches — with today's constant as the default for a definition stating none. Shopify's own rules then decide the outcome from the code's setting and the site discount's, the way they do for any two of the shop's own discounts. Alternative considered: keep one store-wide constant; rejected, because a merchandiser who wants one promotion to stack with member coupons and another not to has no way to say so.

**A code the shop sets aside for a better site discount is not a refusal.** Shopify's documented rule for two discounts that cannot combine is that the better one for the cart applies and the other is dropped. Today `shopifyProvider` compares every requested code against the codes the created draft landed and answers `couponRefused` for any it skipped, which `checkout.ts` turns into a failed order — so the first non-combinable automatic that beats a coupon fails every checkout carrying one. The provider keeps that comparison but splits the answer: a requested code missing from the draft while the draft carries an automatic discount is `couponReplaced`, and only a code missing with no automatic on the draft stays `couponRefused`. On `couponReplaced` the checkout continues on the draft as priced, `releaseCouponTender` returns the coupon to the wallet and the mint is marked dead and deactivated through the same path a `failed` order uses, and the checkout's outcome carries the coupon's name so the member reads that the sale gave more and the coupon is kept. This is the online reading of the till's own trim-to-landed pass, which already frees "a code it dropped". Whether the draft-order response names the applied automatic discount plainly enough to tell the two apart is what `add-site-wide-discounts` task 2.3 records; until it does, the split is designed and not shipped.

**`resolveCoupons()` refuses more than one requested code, full stop, covering every path a coupon can ride, including a reward's own `couponId`** — replacing the narrower `order`-only check. `requested.length > 1` refuses in `resolveCoupons()` before evaluation; `reserveRewardCoupon()`, which takes a reward's `couponId` directly and never calls `resolveCoupons()`, gains the same check against the basket's existing codes before it reserves. This change is the sole owner of that rule end to end. Alternative considered: allow multiple and pick the best value automatically; rejected — the proposal decided the collector picks, and grade10 has no product ranking to substitute for that choice.

**The wire carries the code or the line discount, never both.** `order_items.discountMinor` is wire input, not record-keeping: `checkoutRequest.ts` copies it to `lineItems[].discountMinor` and `shopifyProvider` turns it into a real per-line discount on the draft. Left as-is beside a minted code, every online coupon is taken twice. The record stays — `discountBesidesPointsMinor` sums that column and the points arithmetic depends on it — and the wire is stripped: `buildCheckoutRequest` subtracts, by variant, the cuts of every ride whose code it is sending, and the reward's cuts from `order.loyaltyCouponApplication`.

A gift needs its own clause, because a gift's evaluation carries `gift` and an empty `lineCuts`, and `promise.ts` welds the whole gift line independently of any ride — so no ride-based subtraction reaches it. When a gift rides as a code its line's `discountMinor` is written as zero and the code carries the whole benefit, which is exact under order-claim-time minting because the line's price is known when the code is minted. At the till a gift carries no code at all, because the extension adds that line and zeroes it from `plan.gifts` unconditionally in every build there is — a gift arriving with a code as well would take the gift free and take its price off the rest of the sale.

**An un-updated till needs no coordinated deploy.** The transport moves in the backend, not the extension: `planTillSale` mints for every ride but the gift and sends `welds: []`, and every build there is already executes both `plan.welds` and `plan.codes`. So a till on yesterday's build stops receiving welds and starts receiving a code, and applies it through the `addCartCodeDiscount` it has always had, while its `setLineItemDiscount` path goes quiet on its own. `minClientVersion` rises when the picker build is live and a till has to refuse a second coupon — a version gate the POS lane can actually give, unlike a simultaneous deploy.

**`couponDiscountMinor` is every coupon cut on the order, subtracted exactly once.** Summed from each ride's `orderCutMinor` and `lineCuts` plus the reward's, with `facts.orderCodeMinor` folded into it and deleted — the two are accumulated from the same `evaluation.orderCutMinor` today and subtracting both would under-allow a member's points against their own basket.

**Accepted risk: grade10 prices every benefit it computes locally against a basket the shop may discount further.** The points basis, and a percentage benefit's base and its ceiling alike, are computed before the shop's own automatic-discount allocation is known — `orders/promise.ts` writes the order row before the draft-order call returns `totalDiscountsSet`. A £100 line under a 50% automatic sale with a "20% capped at £30" coupon mints a £20 code against a line the shop then sells for £50, so the coupon takes 40% of the sale price. This is not a combination nobody expects: `discounts.md`'s decisions table records "Points always redeem, even on a product special sale" as Decided. Documented as an accepted gap rather than solved — deferring local pricing past the provider round-trip is a materially larger change. `add-site-wide-discounts`' staging matrix records the observed allocation; revisit on what it reports.

## Service Interfaces

**`codeSays(definition, evaluation, giftPrices) -> { amountMinor, target } | null`** (new, `services/coupons/mintOrder.ts`) — what a code must say, read off the cut the evaluator made against this basket. `null` refuses the mint.

**`mintDiscountCode(deps, params) -> outcome`** (new, extracted from `createCoupon()`'s loop into a shared module inside `packages/grade10-store/backend`) — `params` carries the value, the `CodeTarget`, a customer-scoped `codeScope`, `endsAt`, `combinesWith` (from the coupon's definition, defaulting to today's constant), and the code text. Returns the outcome union `createCodeDiscount` already does. **The caller supplies the code**: an order-keyed mint derives its suffix from the resolved order id and the coupon id, so a retry after a crash re-derives the same code, Shopify answers `codeTaken`, and `discountByCode` returns the node — idempotency and recovery with no pre-write. `create.ts`'s random-suffix rationale ("anything computed from an id is enumerable by whoever holds one coupon") does not apply: the inputs are two v4 UUIDs and every code is customer-scoped.

**`resolveCoupons()`** — signature unchanged; `CheckoutCouponFacts` drops `orderCodes`, which nothing outside a test read — the shop's codes come from `coupon_mints` — and carries `couponDiscountMinor` beside the `lineDiscounts` the order items are still written from; the `requested.length > 1` refusal; and a `SELECT ... FOR UPDATE` on the requested coupon rows inside the transaction that inserts `order_coupons`.

**`mintOrderCodes(order, rides, reward, deps)`** (new, called from `checkout.ts` between `promiseOrder` and `buildCheckoutRequest`, and from the till's plan step) — the one place any code is minted. Reads or writes the `coupon_mints` row for a store ride keyed `(order.id, couponId)`, and the `orders` row's own code columns for a reward. Reuses a `live` row rather than minting again.

**`reserveRewardCoupon()`** (`orders/promise.ts`) — gains the one-discount-code check, and **mints nothing**. It reserves through loyalty's `CouponTender` and returns, exactly as today.

**`shopifyProvider.createDraftOrder()`** — its code comparison answers `couponReplaced` for a requested code the draft did not land while the draft carries an automatic discount, and `couponRefused` only where no automatic explains the gap. `checkout.ts` handles `couponReplaced` by continuing on the draft as priced, releasing the coupon tender, deactivating the mint, and naming the coupon in the outcome the member reads.

**`buildCheckoutRequest()`** (`orders/checkoutRequest.ts`) — `discountCodes` widens from `coupon.kind === "order"` to every kind now riding as a code, and adds the reward's code from the `orders` row. Per-line `discountMinor` is sent net of every cut whose code is in the request.

**`orders/eventSink.ts`'s `rewardArtifact()`** — the artifact for `order.loyaltyCouponUsageId` reports `{ provider: "shopify", kind: "discount_code", externalId: nodeId, code }` from the order row's own columns. The `draft_line_discount` fallback stays only for a reward settled before this change shipped, bounded on the order's `createdAt` against `CODES_SINCE` rather than on a column being absent — after that instant, absent means a lost mint, and it is counted and logged rather than written into loyalty's permanent record as plausible history.

## Risks / Trade-offs

- **A code targeting resolved variant ids is exact for the basket it was minted against, and only that basket.** A basket edited after the mint can carry the code against lines it no longer names. Online this is closed by the mint sitting after the order row commits, so the basket is fixed; at the till it is what the re-plan rule above exists to answer.
- **Extending `resolveCoupons()`'s one-code refusal changes behaviour for any basket that today combines a product/gift coupon with an order coupon** → the product decision the proposal already made, and a real behaviour change: `test/services/checkout.test.ts` and `test/services/pos/sale/sale.test.ts` both currently combine a product coupon and a gift and assert the combined cut. **The backend refusal must not reach production ahead of the "collector picks one" UI** — an untouched frontend turns a working basket into an unexplained refusal.
- **A member holding a pre-change `product`/`gift` coupon** has a code Shopify has never heard of. No backfill is needed and none is run: those rows stop sending their stored code and mint at claim time like any other. Their `coupons.code` stays the member-facing string; the minted code is never shown.
- **The single-code removal gap at the till** — a code can only be cleared by "Remove every discount", and a gift or product coupon inherits that once it rides as a code. **Accepted**: a genuine single-code removal path is materially larger scope. Recorded as a deliberate trade-off, not parity. It is also why the re-plan rule refuses rather than re-mints.
- **A replaced coupon is learned at submit, not in the cart.** The preview is local and mints nothing, so the member sees the coupon's cut in the cart and learns the sale beat it only after submit. Accepted: the order still completes and the coupon is kept, so the cost is a message rather than a failed checkout. The cart's own presentation of the outcome is `present-cart-site-sale-promo-outcomes`.
- **"Remove every discount" cannot confirm once a site-wide automatic discount exists** — `removeAllDiscounts(false)` preserves automatics by design, while the settle predicate waits for `cart.discounts` to be empty, so staff always read the incomplete sentence. The predicate must mean what its comment says: settled when nothing of ours and no code entry remains. This is the one hard coupling between this change and `add-site-wide-discounts`.
- **The guard that retires counter collection is a vendor belief three recorded release gates were written to test, and none has been run** — gates 1 (a customer-scoped `usageLimit: 1` code applies at tender after the customer is attached), 5 (two terminals cannot both complete one single-use code) and 10 (a code deactivated after `addCartCodeDiscount` — is it revalidated at tender?). ❓ until each is recorded with date and tester.
- **A collector applying more than one coupon is not precomputed anywhere** — `tillPanelCoupon()` and `listSpendableCoupons()` both list every live coupon with no basket check, so the picker needs `evaluateCouponsEligibility(basket, coupons)` behind it, not a refusal-and-retry loop.
- **Split lines** — a customer-scoped, variant-targeted code applied cart-wide where the same variant appears on two lines (one paid, one meant free) is unverified against Shopify's entitlement behaviour. `appliesOnEachItem: false` means the amount comes off once, which matches the evaluator's total; what is unresolved is whether a fixed amount larger than the entitled line's value clamps or spills.

## Migration Plan

Additive but for one relaxing constraint edit. `ck_coupons_shape` requires `shopify_node_id is not null` for `kind = 'order'`; since `createCoupon()` stops minting, that clause is dropped. Relaxing a CHECK needs no `NOT VALID`, no `VALIDATE`, no ordering against any backfill, blocks no writer, is safe against every historical row state including the pre-vocabulary arm, and is reversible. The `shopify_node_id is null` clauses for `product` and `gift` stay true and stay as they are. `coupons.shopify_node_id` keeps its already-minted values for pre-change order coupons and is read for them; nothing new writes it.

Ship that alongside the additive `coupon_mints` table and the `orders` row's two new nullable code columns. Because the constraint edit only relaxes, the migration is safe to apply by hand ahead of the code, which is how this repository applies every migration.

Verify on staging, before group 3 reaches production: a facet-scoped product coupon on a basket holding two IP worlds mints a code targeting only the eligible variants; a gift mints against the line's real price and its line is sent at zero; a percentage-with-ceiling coupon mints only at submit and never during a price preview; a reward coupon settles reporting `kind: "discount_code"`; two coupons at once are refused, including a reward alongside a typed code; a submitted, abandoned and resubmitted checkout leaves exactly one live code; a POS re-plan reuses its mint and never stacks a second code; a sale carrying a site-wide automatic discount can still be cleared by "Remove every discount"; and a coupon checkout under an automatic discount that beats it completes at the shop's price with the coupon back in the wallet.
