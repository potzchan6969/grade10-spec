## Context

`packages/grade10-store/backend/src/services/coupons/create.ts` — `createCoupon()` already mints a real Shopify Discount (`deps.discounts.createCodeDiscount`) for an `order`-kind coupon, at redemption time, then compensates (`deactivateCodeDiscount`) if the local insert that follows fails. A `product` or `gift` coupon takes a separate branch today that inserts a plain row with a generated code and mints nothing.

`packages/grade10-store/backend/src/services/coupons/apply.ts` — `resolveCoupons()` is the shared pricing evaluator (web and POS both call it). It already refuses a second `order`-kind code in one request (line ~162), but a `product` or `gift` coupon can still resolve alongside an `order` coupon today, welding `lineDiscounts` independently of `orderCodes`.

`coupons.md`'s own Validity rule already commits every coupon to its reward's definition "as it stood on the day it was bought" — a coupon is deliberately frozen at redemption, never recomputed against a later catalog state. That existing philosophy is what makes most of this change cheap: minting at redemption, the same moment `order` already does it, is not a new risk class for a `gift` or a flat-amount `product` coupon — it is the same one the store already accepts.

## Goals / Non-Goals

**Goals:**
- A `product` and a `gift` coupon each carry their own real Shopify Discount, the same as `order` does today.
- A checkout never carries more than one discount code, however it got there.

**Non-Goals:**
- Changing coupon eligibility, threshold, or redemption rules.
- A new Shopify discount value type — everything mints as `fixed_amount`, computing percentage-with-ceiling locally first, exactly as the evaluator already does for a weld.

## Decisions

**Mint timing splits on whether the cut's money value is knowable at redemption.**

| Coupon shape | Money value | Mint timing |
| --- | --- | --- |
| Order coupon | Fixed, from the definition | At redemption (unchanged) |
| Gift | The gift variant's catalog price at redemption | At redemption |
| Product coupon, fixed-amount benefit | Fixed, from the definition | At redemption |
| Product coupon, percentage-with-ceiling benefit | `min(percentage × eligible line total, ceiling)` — depends on the basket at checkout | At checkout submit, never at a price preview |

The first three extend `createCoupon()`'s existing Shopify-minting branch (currently gated to `definition.kind === "order"`) to also cover `gift` and a fixed-amount `product` coupon — reusing `codeScope`, `shopTarget`, `COMBINES_WITH`, and `compensateMint` exactly as written. A gift's mint additionally needs the resolved variant's current catalog price (`deps.catalog`), looked up once at redemption alongside the existing `resolveVariantRef` call.

The fourth shape cannot be pre-minted: its value depends on a basket that does not exist yet at redemption. It keeps using the local evaluator (`evaluateCoupon`, already used for the weld today) to compute the cut against the real basket, but only at the checkout that will spend it — never during `calculateDraftOrder`'s price preview, which keeps using the local number for display. Minting happens once, immediately before `createDraftOrder`.

**Which mint-timing row a coupon takes is a named, derived property, not a re-derived conditional.** `canMintAtRedemption(definition): boolean` lives beside `evaluateCoupon` in `@grade10/coupons-contracts` — `true` for `order`, `gift`, and a fixed-amount `product` benefit, `false` for a percentage-with-ceiling `product` benefit. `create.ts`'s minting branch and the new checkout-submit mint call both branch on this one function, not on independently re-derived `kind`/benefit-shape checks — so a future coupon shape whose value isn't fixed at redemption is one new case in one place, not a second site to remember.

**One generate-code/retry/compensate implementation, shared by both mint call sites.** `create.ts`'s existing loop (code generation, retry on `codeTaken` up to `MINT_ATTEMPTS`, repair-then-refuse on `customerRefused`, `compensateMint`/`deactivateCodeDiscount` on a later failure) is extracted into `mintDiscountCode(deps, params) -> outcome`, parametrized by the value/target/scope to mint. `createCoupon()`'s redemption-time branch and the new checkout-submit path both call it — one implementation of Shopify code-minting and its failure handling, not two independently maintained copies.

**A mint persists its `nodeId` before the caller can act on it, keyed for idempotent retry.** Every mint — redemption-time or checkout-submit — writes `{ orderId, couponId, nodeId, code }` into a new `coupon_mints` row (or an equivalent column on `order_coupons`) inside the same transaction that follows it, before the draft order is created. A retry of the same checkout submission (client timeout, duplicate tap, `checkoutRequest.ts`'s own "recovery re-issue") looks up that row first and reuses the prior mint instead of minting again. `adoptUnreportedCodes` (`coupons/settle.ts`) drops its `eq(coupons.kind, "order")` filter so it can adopt a `product`/`gift` code the shop honored with no matching promise, the same way it already adopts an `order` code today. An order that is canceled, expired, or superseded (`orders/retire.ts`'s `supersedePromisedOrders`) deactivates any mint recorded against it that never settled.

**Product and gift codes are scoped to the redeeming member unconditionally**, not gated on `onlineCodeScope === "customer"` the way an order coupon's `codeScope()` is today. Minting a product coupon or a gift as a real Shopify code makes it a bearer string for the first time — before this change it only ever resolved inside `resolveCoupons()`, which enforces the `not_owner` ownership check before any money moves; a real code redeemed at Shopify's hosted checkout field or POS's native discount box bypasses that check entirely. Order coupons keep today's `onlineCodeScope`-gated behavior (an accepted, existing trade-off); product and gift codes always scope to the member's paired Shopify customer, closing the new bearer-theft surface this change would otherwise open for shapes that never had it.

**`resolveCoupons()` refuses more than one requested code, full stop, and this rule covers every path a coupon can ride, including a reward's own `couponId`** — replacing the narrower `order`-only check, and covering "a coupon is the order's one discount" (previously drafted separately in `deliver-reward-coupons` as `grade10-site-loyalty-programme-SC-163`, dropped there in favor of this one). `requested.length > 1` refuses immediately in `resolveCoupons()`, before evaluation. `orders/promise.ts`'s `reserveRewardCoupon()` — which takes a reward's `couponId` directly and never calls `resolveCoupons()` — gains the same check against `facts.discountCodes`/any already-riding reward coupon before it reserves, so a reward coupon and a typed code or store coupon refuse each other the same way two typed codes already do. This change is the sole owner of the one-discount-code rule end to end; `deliver-reward-coupons` does not implement its own copy (see that change's tasks.md). Alternative considered: allow multiple and pick the best value automatically; rejected — the proposal decided the collector picks, and grade10 has no product ranking to substitute for that choice.

**`CheckoutCouponFacts` gains `discountCodes: readonly string[]` and keeps a `couponDiscountMinor` money total, replacing the `orderCodes` / `lineDiscounts` split for anything code-shaped.** A `gift`, a fixed `product` coupon, and an `order` coupon all resolve to one already-minted code, added to `discountCodes`. A percentage-with-ceiling `product` coupon resolves to a computed amount that the checkout-submit step mints just before use. `lineDiscounts` stays only for what still welds — nothing, once this change ships, other than points. The money value a coupon carries does not disappear with the weld: `couponDiscountMinor` (summed from each ride's `evaluation.orderCutMinor`/`evaluation.lineCuts`, the same numbers the evaluator already produces) is the one field both `orders/promise.ts`'s points-basis calculation and `pos/sale/sale.ts`'s `weldsOf()` per-line display read instead of scanning `lineDiscounts` — both call sites are updated to read it, since neither can keep working against a map that a minted coupon no longer populates.

## Service Interfaces

**`mintDiscountCode(deps, params) -> outcome`** (new, extracted from `createCoupon()`'s existing loop into a shared module both call sites import) — generates a code, calls `createCodeDiscount`, retries on `codeTaken` up to `MINT_ATTEMPTS`, repairs-then-refuses on `customerRefused`. Returns the same outcome union `createCodeDiscount` already does (`{ outcome: "minted"; code; nodeId }`, or `codeTaken` / `customerRefused` / `rejected` / `throttled`). `createCoupon()`'s redemption-time branch and `mintComputedCouponCode()` (below) both call this instead of each carrying their own copy of the loop.

**`resolveCoupons()`** — signature unchanged; behavior changes in what `CheckoutCouponFacts` carries (`discountCodes` + `couponDiscountMinor`, replacing `orderCodes`/`lineDiscounts` for coupon shapes), the new `requested.length > 1` refusal, and a lock taken on the requested coupon rows (see Risks) before any mint runs.

**`mintComputedCouponCode()`** (new, `coupons/apply.ts` or a sibling module) — called only from the checkout-submit path, never from a price preview; the distinction is structural, not a one-time confirmation (see Risks):
- **Input:** the single resolved `CouponRide` for a percentage-with-ceiling product coupon, the computed `cutMinor`, an idempotency key (`orderId` + `couponId`), and the mint deps (`discounts`, `config`, `clock`).
- **Success:** `{ outcome: "minted"; code: string; nodeId: string }` — or, if a `coupon_mints` row already exists for this idempotency key, the prior mint is returned unchanged instead of minting again.
- **Failure:** the same outcome union `mintDiscountCode` returns.
- **Persistence:** the `{ orderId, couponId, nodeId, code }` row is written before `createDraftOrder` runs, in the same transaction. Compensation on a later failure deactivates the node and removes the row.

**`reserveRewardCoupon()`** (`orders/promise.ts`) — gains the one-discount-code check described in Decisions, refusing where the basket already carries a discount code from any other source.

## Risks / Trade-offs

- **A gift or a fixed-amount product coupon's price is frozen at redemption, same as an order coupon already is** → Not a new risk: `coupons.md`'s Validity rule already commits to this for every coupon. No mitigation needed beyond what already exists.
- **Extending `resolveCoupons()`'s one-code refusal changes behavior for any basket that today combines a product/gift coupon with an order coupon** → This is the product decision the proposal already made (collector picks one), and it is a real product-behavior change beyond "generalize the order-only rule," not a mechanical fixture update: `test/services/checkout.test.ts` (~line 503, `couponCodes: ['cut-aaa', 'gift-bbb']`) and `test/services/pos/sale/sale.test.ts` (~line 478) both currently combine a product coupon and a gift and assert the combined cut. Update both explicitly, and do not ship the backend refusal (task group 3) ahead of the "collector picks one" UI (task group 5) — an untouched frontend would otherwise turn a working basket into an unexplained refusal.
- **`resolveCoupons()`'s "riding another open checkout" read is a plain `SELECT`, not a lock** (`openRiders()`, outside `orders/promise.ts`'s transaction) — before this change, a lost race only double-welded a local number with no external effect. After it, two concurrent callers (a resumed web tab and a POS session on the same coupon, or a same-user retry) can each independently mint a real, `usageLimit: 1` Shopify Discount for the same coupon row; only one can ever settle, and the mint-persistence above (see Decisions) is what lets the other be found and deactivated rather than orphaned forever. Close the race itself with a `SELECT ... FOR UPDATE` on the requested coupon rows inside the transaction that later inserts `order_coupons`, or a DB-level partial unique constraint on "one open ride per coupon id."
- **The frontend and the POS extension currently let a collector apply more than one coupon without being asked to choose, and neither side precomputes which of a collector's coupons would actually pass basket evaluation** → `tillPanelCoupon()` (POS) and `listSpendableCoupons()` (web) both list every live coupon with no basket check, so "present the choice" (task group 5) needs a server-side eligibility precheck (a dry-run `evaluateCoupon` against the basket) feeding the picker, not just a refusal-and-retry loop. Give task group 5 its own `ui-design.md`.
- **POS has no preview/submit split for the percentage-with-ceiling mint-timing rule** — the web checkout's `calculateDraftOrder` vs `createDraftOrder` distinction doesn't exist at the till; `discounts.md`'s POS mechanism describes Apply (re-plannable, up to 20 times per 5 minutes) as the step where a coupon's code is expected to land. Pin mint timing to Tender, not Apply, for this coupon shape specifically; Apply keeps showing the local evaluator's number, the same way `calculateDraftOrder` does online.
- **The real till extension (`integrations/shopify-pos/grade10`), not just the backend POS simulator, still welds** — `src/acts/flow.ts` calls `host.setLineItemDiscount(...)` to zero a gift line, the exact mechanism this change retires. The simulator (`services/pos/simulator/`) is a backend rehearsal tool, not the staff-facing extension; both need the discount-code transport, or the extension is explicitly deferred to a named follow-on change.
- **`confirmTillSale`, `settle.ts`'s `corroborates()`, and `weldsOf()` still key `product`-kind reconciliation off `orderCouponCuts` weld rows** — once a product coupon rides as a code instead of a weld, no such rows exist, so a landed discount would be misclassified as dropped and its `order_coupons` row deleted. Match `product` by code, the same way `order` already is, everywhere these three functions branch on kind.

## Migration Plan

Not purely additive: `coupons.ts`'s `ck_coupons_shape` CHECK constraint currently requires `shopify_node_id is null` for both `kind = 'product'` and `kind = 'gift'` — the opposite of what this change's minting branch writes. Ship a migration rewriting that constraint to allow a non-null `shopify_node_id` for `product` and `gift` kinds, sequenced before or atomic with task group 1, plus a `coupon_mints` table (or equivalent column) for the idempotency record in Decisions.

Existing product/gift coupons minted under the old weld-only scheme (`shopifyNodeId: null`, a code Shopify has never heard of) stay live for up to `MAX_COUPON_VALID_DAYS` (365) after deploy. `shopifyProvider.ts` already refuses loudly rather than silently mispricing when a requested code fails to land (`outcome: "couponRefused"`), so the immediate risk is availability, not silent mispricing — but a member holding a pre-change coupon would otherwise see every attempt to spend it refused. Backfill-mint a real Shopify Discount for every currently-live product/gift coupon row as part of the deploy (a one-time, idempotent, logged script), and exercise one such backfilled coupon against the post-change checkout on staging, not only freshly-redeemed ones.

Verify on staging: redeem one product coupon and one gift, confirm each mints a real Shopify Discount and settles a real checkout by it; redeem a percentage-with-ceiling product coupon, confirm it mints only at submit and never during a price preview; attempt to apply two coupons at once (including a reward coupon alongside a typed code) and confirm the refusal; submit, abandon, and resubmit the same checkout with the same coupon and confirm only one code is ever live; run a POS sale spending a product coupon and confirm settlement, Undo, and unreported-code adoption all still work.
