## Context

`packages/grade10-store/backend/src/services/coupons/create.ts` — `createCoupon()` already mints a real Shopify Discount (`deps.discounts.createCodeDiscount`) for an `order`-kind coupon, at redemption time, then compensates (`deactivateCodeDiscount`) if the local insert that follows fails. A `product` or `gift` coupon takes a separate branch today that inserts a plain row with a generated code and mints nothing.

`packages/grade10-store/backend/src/services/coupons/apply.ts` — `resolveCoupons()` is the shared pricing evaluator (web and POS both call it). It already refuses a second `order`-kind code in one request (line ~162), but a `product` or `gift` coupon can still resolve alongside an `order` coupon today, welding `lineDiscounts` independently of `orderCodes`.

**A loyalty reward's coupon is a separate thing from a store coupon, and this change has to mint for both.** `packages/loyalty/backend/src/services/rewards/coupons.ts`'s `couponInstances`/`couponUsages` never touch `packages/grade10-store/backend/src/db/schema/coupons.ts`'s `coupons` table — a reward is redeemed, held, and settled entirely inside loyalty's own tables, reached from the store only through the `CouponTender` port (`orders/promise.ts`'s `reserveRewardCoupon()` calls `coupons.reserve()`/`coupons.settle()`). `couponUsages.providerArtifact` already carries a `kind: "discount_code" | "draft_order_discount" | "draft_line_discount"` union (`@grade10/loyalty-contracts`) — the schema already anticipated a coupon settling by a real Shopify code — but nothing produces `"discount_code"` today: `orders/eventSink.ts`'s `ownedEvent()` always builds `kind: "draft_line_discount"` for a reward coupon, with the comment "a reward coupon is always a weld ... a shop code is the registry's, and never lands here." That comment is the fact this change has to make false for a reward coupon the same way it already makes it false for a `product`/`gift` store coupon.

`coupons.md`'s own Validity rule already commits every coupon to its reward's definition "as it stood on the day it was bought" — a coupon is deliberately frozen at redemption, never recomputed against a later catalog state. That existing philosophy is what makes most of this change cheap: minting at redemption, the same moment `order` already does it, is not a new risk class for a `gift` or a flat-amount `product` coupon — it is the same one the store already accepts.

## Goals / Non-Goals

**Goals:**
- A `product` and a `gift` coupon each carry their own real Shopify Discount, the same as `order` does today.
- A reward's own coupon (`orders/promise.ts`'s `reserveRewardCoupon()` path) carries a real Shopify Discount too, by the same mechanism — this is what `deliver-reward-coupons` task group 3 depends on to retire the till's collection-confirm step.
- A checkout never carries more than one discount code, however it got there.

**Non-Goals:**
- Changing coupon eligibility, threshold, or redemption rules.
- A new Shopify discount value type — everything mints as `fixed_amount`, computing percentage-with-ceiling locally first, exactly as the evaluator already does for a weld.
- Giving `packages/loyalty/backend` a Shopify integration of its own. A reward's coupon mints through the store side, the same package and the same helper every other coupon shape mints through — loyalty only ever receives back a `providerArtifact` describing what the store minted, the same way it already receives one for today's weld.

## Decisions

**Mint timing splits on whether the cut's money value is knowable at redemption, and whether an order exists yet.**

| Coupon shape | Money value | Order exists at mint time? | Mint timing | Where the mint is recorded |
| --- | --- | --- | --- | --- |
| Order coupon | Fixed, from the definition | No | At redemption (unchanged) | `coupons.shopify_node_id` |
| Gift (store coupon) | The gift variant's catalog price at redemption | No | At redemption | `coupons.shopify_node_id` |
| Product coupon, fixed-amount benefit | Fixed, from the definition | No | At redemption | `coupons.shopify_node_id` |
| Product coupon, percentage-with-ceiling benefit | `min(percentage × eligible line total, ceiling)` — depends on the basket | Yes | At checkout submit, never at a price preview | `coupon_mints` row |
| A reward's own coupon (any kind) | From the reward's definition, evaluated against the real basket | Yes — `reserveRewardCoupon()` only runs once an order is being promised | At order-promise time, in the same call that reserves the coupon | `coupon_mints` row |

The first three extend `createCoupon()`'s existing Shopify-minting branch (currently gated to `definition.kind === "order"`) to also cover `gift` and a fixed-amount `product` coupon — reusing `codeScope`, `shopTarget`, `COMBINES_WITH`, and `compensateMint` exactly as written. A gift's mint additionally needs the resolved variant's current catalog price (`deps.catalog`), looked up once at redemption alongside the existing `resolveVariantRef` call. Because no order exists yet, these three write `shopify_node_id` directly onto their own `coupons` row — there is nothing to key a `coupon_mints` row by, and none is written.

The last two shapes cannot be pre-minted, for different reasons: a percentage-with-ceiling product coupon's value depends on a basket that doesn't exist at redemption; a reward's coupon has no order to mint against until `reserveRewardCoupon()` runs. Both mint order-keyed, through the same `coupon_mints` table, at the point an order first claims them — never during a price preview.

**Which mint-timing row a coupon takes is a named, derived property, not a re-derived conditional.** `canMintAtRedemption(definition): boolean` lives beside `evaluateCoupon` in `@grade10/coupons-contracts` — `true` for `order`, `gift`, and a fixed-amount `product` benefit, `false` for a percentage-with-ceiling `product` benefit. It answers only for store-table coupons; a reward's coupon is never redemption-minted at all (no order exists then), so it isn't a third value of this function — it's the third row of the table above, always order-keyed. `create.ts`'s minting branch and the new checkout-submit mint call both branch on `canMintAtRedemption`, not on independently re-derived `kind`/benefit-shape checks.

**One generate-code/retry/compensate implementation, shared by every mint call site.** `create.ts`'s existing loop (code generation, retry on `codeTaken` up to `MINT_ATTEMPTS`, repair-then-refuse on `customerRefused`, `compensateMint`/`deactivateCodeDiscount` on a later failure) is extracted into `mintDiscountCode(deps, params) -> outcome`, parametrized by the value/target/scope to mint, and kept inside `packages/grade10-store/backend` — every caller (`createCoupon()`, the new checkout-submit path, `reserveRewardCoupon()`) already lives in that package, so nothing needs to leave it. One implementation of Shopify code-minting and its failure handling, not three independently maintained copies.

**`coupon_mints` is order-keyed, exists for exactly the two shapes that mint against an order rather than at redemption, and its `couponId` is not a foreign key.** Every such mint writes `{ orderId, couponId, nodeId, code, origin }` into a `coupon_mints` row inside the same transaction that follows it, before the draft order is created — `origin` is `"store_coupon"` or `"reward_coupon"`, recorded for observability, since `couponId` alone can't say which: a percentage-with-ceiling product coupon's `couponId` is `coupons.id` (a UUID), a reward's is loyalty's own `couponInstances.id` (an opaque text id from a different database entirely) — `coupon_mints.couponId` is a plain text column with no `references()`, deliberately, because it has to hold either. A retry of the same checkout submission (client timeout, duplicate tap, `checkoutRequest.ts`'s own "recovery re-issue") looks up that row first by `(orderId, couponId)` and reuses the prior mint instead of minting again — a real DB unique constraint on `(orderId, couponId)` makes a genuinely concurrent double-submit fail on the second insert rather than racing, the same way `order_coupons`' own primary key already does. `adoptUnreportedCodes` (`coupons/settle.ts`) drops its `eq(coupons.kind, "order")` filter so it can adopt a `product`/`gift` code the shop honored with no matching promise, the same way it already adopts an `order` code today. An order that is canceled, expired, or superseded (`orders/retire.ts`'s `supersedePromisedOrders`) deactivates any `coupon_mints` row recorded against it that never settled — for a reward-coupon mint specifically, this pairs with releasing the loyalty-side reservation (`releaseReward`, already called on the same refusal paths in `promise.ts`), so a dead order neither holds the member's coupon nor leaves an orphaned live code.

**A reward's own coupon mints inside `reserveRewardCoupon()`, through the same helper and the same table as a percentage-with-ceiling product coupon — not a new mechanism.** Once loyalty's `coupons.reserve()` returns `"reserved"`, `reserveRewardCoupon()` calls `mintDiscountCode()` with the reserved evaluation's cut, keyed by `(orderId, args.couponId)`, and writes the `coupon_mints` row (`origin: "reward_coupon"`). If the mint fails, `reserveRewardCoupon()` releases the loyalty reservation (`releaseReward`) the same way it already does on every other refusal path, and refuses the promise — a member never ends up with a coupon marked `reserved` against an order that never got a code. The minted code rides the draft order's `discountCodes` the same as every other coupon (see `discountCodes`/`couponDiscountMinor` decision below); `checkoutRequest.ts` and `pos/settle.ts` gain a small reward-specific read of the `coupon_mints` row keyed by `order.loyaltyCouponId`, mirroring the reward-specific branch `orders/eventSink.ts` already carries for `order.loyaltyCouponUsageId` (see Service Interfaces). Once a settlement corroborates the code (the same `corroborates()` matching every other code-shaped coupon uses), `eventSink.ts`'s `providerArtifact` construction stops hardcoding `kind: "draft_line_discount"` and reports `kind: "discount_code"` with the minted `nodeId`/`code` instead — the comment claiming "a shop code ... never lands here" is deleted along with the behavior it described. This is what actually gives `deliver-reward-coupons` task 3.2 the guard it was written to depend on: Shopify itself refuses a second redemption of the `usageLimit: 1` code, and the `(orderId, couponId)` uniqueness on `coupon_mints` stops two concurrent reservations of the same reward coupon from each minting their own.

**Product, gift, and reward codes are all scoped to the redeeming member unconditionally**, not gated on `onlineCodeScope === "customer"` the way an order coupon's `codeScope()` is today. Minting any of them as a real Shopify code makes it a bearer string for the first time — before this change a `product`/`gift` coupon only ever resolved inside `resolveCoupons()`, which enforces the `not_owner` ownership check before any money moves, and a reward's coupon only ever resolved inside loyalty's own ownership-checked `useCoupon()`; a real code redeemed at Shopify's hosted checkout field or POS's native discount box bypasses both checks entirely. Order coupons keep today's `onlineCodeScope`-gated behavior (an accepted, existing trade-off); every other shape always scopes to the member's paired Shopify customer, closing the bearer-theft surface this change would otherwise open. This applies at every mint call site the same way — `createCoupon()`'s redemption-time branch, `mintComputedCouponCode()`'s checkout-submit path, and `reserveRewardCoupon()`'s new mint — none of them fall back to `{kind: 'all'}`. **A member with no paired Shopify customer at mint time refuses the mint** (and, for a reward, refuses the whole reservation) rather than minting an unscoped code — a customer-scoped code with nothing to scope it to is not a safe fallback, it's the same bearer-theft gap this decision exists to close.

**`resolveCoupons()` refuses more than one requested code, full stop, and this rule covers every path a coupon can ride, including a reward's own `couponId`** — replacing the narrower `order`-only check, and covering "a coupon is the order's one discount" (previously drafted separately in `deliver-reward-coupons` as `grade10-site-loyalty-programme-SC-163`, dropped there in favor of this one). `requested.length > 1` refuses immediately in `resolveCoupons()`, before evaluation. `orders/promise.ts`'s `reserveRewardCoupon()` — which takes a reward's `couponId` directly and never calls `resolveCoupons()` — gains the same check against `facts.discountCodes`/any already-riding reward coupon before it reserves (and before it mints — a refused reservation never reaches the mint step), so a reward coupon and a typed code or store coupon refuse each other the same way two typed codes already do. This change is the sole owner of the one-discount-code rule end to end; `deliver-reward-coupons` does not implement its own copy (see that change's tasks.md). Alternative considered: allow multiple and pick the best value automatically; rejected — the proposal decided the collector picks, and grade10 has no product ranking to substitute for that choice.

**`CheckoutCouponFacts` gains `discountCodes: readonly string[]` and keeps a `couponDiscountMinor` money total, replacing the `orderCodes` / `lineDiscounts` split for anything code-shaped.** A `gift`, a fixed `product` coupon, and an `order` coupon all resolve to one already-minted code, added to `discountCodes`. A percentage-with-ceiling `product` coupon and a reward's own coupon both resolve to a computed amount that the checkout-submit/order-promise step mints just before use. `lineDiscounts` stays only for what still welds — nothing, once this change ships, other than points. The money value a coupon carries does not disappear with the weld: `couponDiscountMinor` (summed from each ride's `evaluation.orderCutMinor`/`evaluation.lineCuts`, the same numbers the evaluator already produces) is the one field both `orders/promise.ts`'s points-basis calculation and `pos/sale/sale.ts`'s `weldsOf()` per-line display read instead of scanning `lineDiscounts` — both call sites are updated to read it, since neither can keep working against a map that a minted coupon no longer populates. `weldsOf()` itself needs no aggregate-reading edit beyond this: its coupon-sourced entries simply stop appearing once `lineDiscounts` is no longer populated by a minted coupon. `order_items.discountMinor`'s per-line attribution — which today reads the same weld rows — is repointed at each ride's own `evaluation.lineCuts`, summed by `variantId`, so per-line record-keeping does not silently zero out for a `product`, `order`, or gift-on-its-own-line coupon once the weld stops existing.

**Accepted risk: points-basis is computed before the shop's own automatic-discount allocation is known, and this change does not resolve that.** `add-site-wide-discounts` lets a draft order carry a Shopify automatic discount alongside the order's one discount code; `orders/promise.ts` writes the order row (and its points basis) before the draft-order provider call returns `totalDiscountsSet`, so a site-wide discount's real allocation is architecturally unavailable at the moment points-basis is computed, in both this change and `add-site-wide-discounts`. Documented here as a known, accepted gap rather than solved: deferring points-basis past the provider round-trip would be a materially larger change for a combination (a site-wide automatic discount stacking with points) that is not yet confirmed to happen at all. Revisit only if it's observed causing real over- or under-capture on staging or production.

## Service Interfaces

**`mintDiscountCode(deps, params) -> outcome`** (new, extracted from `createCoupon()`'s existing loop into a shared module inside `packages/grade10-store/backend` that every call site imports) — generates a code, calls `createCodeDiscount`, retries on `codeTaken` up to `MINT_ATTEMPTS`, repairs-then-refuses on `customerRefused`. Returns the same outcome union `createCodeDiscount` already does (`{ outcome: "minted"; code; nodeId }`, or `codeTaken` / `customerRefused` / `rejected` / `throttled`). `createCoupon()`'s redemption-time branch, `mintComputedCouponCode()`, and `reserveRewardCoupon()`'s new mint step all call this instead of each carrying their own copy of the loop. `params` always carries a customer-scoped `codeScope` for every caller except `createCoupon()`'s `order`-kind branch (see Decisions).

**`resolveCoupons()`** — signature unchanged; behavior changes in what `CheckoutCouponFacts` carries (`discountCodes` + `couponDiscountMinor`, replacing `orderCodes`/`lineDiscounts` for coupon shapes), the new `requested.length > 1` refusal, and a lock taken on the requested coupon rows (see Risks) before any mint runs.

**`mintComputedCouponCode()`** (new, `coupons/apply.ts` or a sibling module) — called only from the checkout-submit path, never from a price preview; the distinction is structural, not a one-time confirmation (see Risks):
- **Input:** the single resolved `CouponRide` for a percentage-with-ceiling product coupon, the computed `cutMinor`, an idempotency key (`orderId` + `couponId`), the member's paired Shopify `customerId` (to build the customer-scoped `codeScope`), and the mint deps (`discounts`, `config`, `clock`).
- **Success:** `{ outcome: "minted"; code: string; nodeId: string }` — or, if a `coupon_mints` row already exists for this idempotency key, the prior mint is returned unchanged instead of minting again.
- **Failure:** the same outcome union `mintDiscountCode` returns; a `customerId`-less caller refuses before attempting a mint (see Decisions).
- **Persistence:** the `{ orderId, couponId, nodeId, code, origin: "store_coupon" }` row is written before `createDraftOrder` runs, in the same transaction. Compensation on a later failure deactivates the node and removes the row.

**`reserveRewardCoupon()`** (`orders/promise.ts`) — gains the one-discount-code check described in Decisions, refusing where the basket already carries a discount code from any other source; on a pass, reserves through loyalty's `CouponTender`, then mints through `mintDiscountCode()` keyed by `(orderId, args.couponId)`, persists the `coupon_mints` row (`origin: "reward_coupon"`), and returns the minted code alongside the existing `evaluation` so it rides `discountCodes` the same as any other coupon. A mint failure releases the loyalty reservation before refusing.

**`buildCheckoutRequest()`** (`orders/checkoutRequest.ts`) — its `discountCodes` filter widens from `coupon.kind === "order"` to every kind that now rides as a code (`order`, `product`, `gift`, from `order_coupons`), **and** gains a second source: when `order.loyaltyCouponId` is set, the `coupon_mints` row for `(order.id, order.loyaltyCouponId)` contributes its code too. These are two different tables because a reward coupon has no row in `order_coupons` — its owning record lives in loyalty's `couponInstances`, not `coupons` — so it is read the same way `orders/eventSink.ts` already reads reward-coupon state: keyed off the `loyaltyCouponId`/`loyaltyCouponUsageId` columns already on the `orders` row, not through `order_coupons`.

**`orders/eventSink.ts`'s `ownedEvent()`** — the `providerArtifact` built for `order.loyaltyCouponUsageId` stops always being `kind: "draft_line_discount"`. It looks up the `coupon_mints` row for `(order.id, order.loyaltyCouponId)`; when one exists (every reward coupon, once this change ships), it reports `{ provider: "shopify", kind: "discount_code", externalId: nodeId, code }`; only a reward settled before this change shipped (see Migration Plan) still has no such row and falls back to today's `draft_line_discount` shape.

## Risks / Trade-offs

- **A gift or a fixed-amount product coupon's price is frozen at redemption, same as an order coupon already is** → Not a new risk: `coupons.md`'s Validity rule already commits to this for every coupon. No mitigation needed beyond what already exists.
- **Extending `resolveCoupons()`'s one-code refusal changes behavior for any basket that today combines a product/gift coupon with an order coupon** → This is the product decision the proposal already made (collector picks one), and it is a real product-behavior change beyond "generalize the order-only rule," not a mechanical fixture update: `test/services/checkout.test.ts` (~line 503, `couponCodes: ['cut-aaa', 'gift-bbb']`) and `test/services/pos/sale/sale.test.ts` (~line 478) both currently combine a product coupon and a gift and assert the combined cut. Update both explicitly. **The backend refusal (task group 3) must not deploy to production ahead of the "collector picks one" UI (task group 5)** — an untouched frontend would otherwise turn a working basket into an unexplained refusal; gate group 3's production rollout behind group 5's completion, whether that means shipping them in the same deploy or holding group 3's refusal behind a flag until group 5 lands, since the two can genuinely land on separate PRs under this repository's incremental-deploy model.
- **`resolveCoupons()`'s "riding another open checkout" read is a plain `SELECT`, not a lock** (`openRiders()`, outside `orders/promise.ts`'s transaction) — before this change, a lost race only double-welded a local number with no external effect. After it, two concurrent callers (a resumed web tab and a POS session on the same coupon, or a same-user retry) can each independently mint a real, `usageLimit: 1` Shopify Discount for the same coupon row; only one can ever settle, and the mint-persistence above (see Decisions) is what lets the other be found and deactivated rather than orphaned forever. Close the race itself with a `SELECT ... FOR UPDATE` on the requested coupon rows inside the transaction that later inserts `order_coupons`, or a DB-level partial unique constraint on "one open ride per coupon id." The same race exists for a reward's own coupon in `reserveRewardCoupon()` — closed the same way, by the `(orderId, couponId)` unique constraint on `coupon_mints` (see Decisions), which is a stronger guarantee than a `SELECT ... FOR UPDATE` would be on its own since it holds even across two different order rows racing the same coupon.
- **The frontend and the POS extension currently let a collector apply more than one coupon without being asked to choose, and neither side precomputes which of a collector's coupons would actually pass basket evaluation** → `tillPanelCoupon()` (POS) and `listSpendableCoupons()` (web) both list every live coupon with no basket check, so "present the choice" (task group 5) needs a server-side eligibility precheck (a dry-run `evaluateCoupon` against the basket) feeding the picker, not just a refusal-and-retry loop. This is two separate deliverables: a `ui-design.md` for the choice surface (designer-authored), and a named backend function — `evaluateCouponsEligibility(basket, coupons) -> EligibilityResult[]` — that both `tillPanelCoupon()` and `listSpendableCoupons()` call, added to this document's Service Interfaces once task group 5 is picked up.
- **POS has no "Tender" lifecycle hook to pin a late mint to** — `integrations/shopify-pos/grade10`'s extension source (`src/host/port.ts`, `src/acts/flow.ts`, `src/acts/spend.ts`) only reacts to Apply-time cart edits; there is no callback that fires at the tender moment itself, and `discounts.md`'s own POS mechanism describes minting uniformly at Apply (step 8.4) with no Tender carve-out. **Decision: mint at Apply, the same as every other POS coupon shape**, reusing the idempotency this change already builds (`coupon_mints` keyed by `orderId`/`couponId`) so a re-plan that re-submits the same coupon reuses the same mint rather than minting twice. A basket edited between one Apply and the next that drops or changes the coupon's eligible lines invalidates the prior mint the same way any other dropped benefit is trimmed at POS step 9 — deactivate the stale `coupon_mints` row and mint fresh on the next Apply that still carries the coupon, rather than trying to detect "the same" mint is still valid.
- **The real till extension (`integrations/shopify-pos/grade10`), not just the backend POS simulator, still welds** — `src/acts/flow.ts` calls `host.setLineItemDiscount(...)` to zero a gift line, the exact mechanism this change retires. The simulator (`services/pos/simulator/`) is a backend rehearsal tool, not the staff-facing extension; both need the discount-code transport. This conversion is unverified against Shopify's actual entitlement behavior for a customer-scoped, product-fixed discount code applied cart-wide when the same variant appears on two lines (one paid, one meant free) — confirm this on staging (task group 6) before relying on it, and record what the per-unit-across-split-lines model and the weld's partial-landing signal (`weldPartialSentence`) become under the code transport: retired, or replaced by an equivalent read of which lines a code actually landed on.
- **`confirmTillSale`, `settle.ts`'s `corroborates()`, and `weldsOf()` still key `product`-kind reconciliation off `orderCouponCuts` weld rows** — once a product coupon rides as a code instead of a weld, no such rows exist, so a landed discount would be misclassified as dropped and its `order_coupons` row deleted. Match `product` by code, the same way `order` already is, everywhere these three functions branch on kind; the reward-coupon case matches by `coupon_mints`' code instead, since it never had an `order_coupons` row to begin with.
- **Converting a gift/product coupon to a code retires today's clean single-tap removal at the till** — an order-coupon-shaped discount code can only be cleared by "Remove every discount," not removed on its own, and a gift/product coupon inherits that same limitation once it rides as a code (task group 4.3). **Accepted for this change**: building a genuine single-code removal path is materially larger scope than this change's goal, and "Remove every discount" already exists as the documented fallback (`discounts.md`'s Undo section). Recorded here as a deliberate, product-acknowledged trade-off, not an oversight — do not let task 4.3 read as unremarkable parity.

## Migration Plan

Not purely additive: `coupons.ts`'s `ck_coupons_shape` CHECK constraint currently requires `shopify_node_id is null` for both `kind = 'product'` and `kind = 'gift'` — the opposite of what this change's minting branch writes for most of those rows. The rewritten predicate is exact, not "allow non-null":

- `kind = 'gift'` — `shopify_node_id is not null` required (always minted at redemption).
- `kind = 'product' and benefit_kind = 'fixed'` — `shopify_node_id is not null` required (minted at redemption).
- `kind = 'product' and benefit_kind = 'percentage'` — `shopify_node_id is null` stays required; this shape never writes to its own `coupons` row, only to `coupon_mints` (see Decisions), and stays that way permanently, not just until a backfill catches up.
- `kind = 'order'` — unchanged.

Add the constraint with `NOT VALID` (validated in a separate, later statement once the backfill below has run), because at the moment this migration deploys every pre-change `gift`/fixed-`product` row still has `shopify_node_id is null` — a strictly-validated non-null requirement would fail against them immediately. Ship this alongside the `coupon_mints` table (`orderId`, `couponId` — no foreign key, `nodeId`, `code`, `origin`, a unique constraint on `(orderId, couponId)`) for the idempotency record in Decisions.

Existing product/gift coupons minted under the old weld-only scheme (`shopifyNodeId: null`, a code Shopify has never heard of) stay live for up to `MAX_COUPON_VALID_DAYS` (365) after deploy. `shopifyProvider.ts` already refuses loudly rather than silently mispricing when a requested code fails to land (`outcome: "couponRefused"`), so the immediate risk is availability, not silent mispricing — but a member holding a pre-change coupon would otherwise see every attempt to spend it refused. Backfill-mint a real Shopify Discount for every currently-live `gift`/fixed-`product` coupon row as part of the deploy: a one-time script that, per row, calls `mintDiscountCode()` and writes `shopify_node_id` back in the same transaction as the mint's own persistence step — the existing mint-then-persist-then-compensate-on-failure pattern already makes this safe to re-run after a crash (a row that already has `shopify_node_id` set is simply skipped on the next pass, and a mint whose write failed is compensated the same way any other failed mint is), rather than needing a separate idempotency mechanism of its own. Run the CHECK constraint's `VALIDATE` step only after this backfill completes. Exercise one such backfilled coupon against the post-change checkout on staging, not only freshly-redeemed ones.

Verify on staging: redeem one product coupon and one gift, confirm each mints a real Shopify Discount and settles a real checkout by it; redeem a percentage-with-ceiling product coupon, confirm it mints only at submit and never during a price preview; redeem a reward coupon and confirm it mints at order-promise time and settles reporting `kind: "discount_code"`; attempt to apply two coupons at once (including a reward coupon alongside a typed code) and confirm the refusal; submit, abandon, and resubmit the same checkout with the same coupon and confirm only one code is ever live; run a POS sale spending a product coupon through the real till extension (not the simulator) and confirm settlement, Undo, and unreported-code adoption all still work.
